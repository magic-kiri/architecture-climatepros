ClimatePros · Stream 1 — Unified Architecture

Three use cases, one job · Auto-Dispatch (A) · Job Summarisation (B) · Parts Finder (C) · Azure-first, SQL Server on AWS

1. Stream 1 Overview

ClimatePros runs commercial refrigeration & HVAC field service: ~900–1,000 technicians, 46 branches, 10,000+ sites. Work orders arrive automatically. Everything after that still runs on a phone call and a technician's memory. Three use cases, three bottlenecks, one job.

Where AI sits: Use Case A is a deterministic algorithm — no LLM. It replaces a decision a dispatcher already makes by hand, so it must be explainable and repeatable. Use Cases B and C use AI, and in both the technician can always override it.

Auto-Dispatch — finding the right technician

Web portal · Dispatcher

Confirming a tech today means dialling ~40 candidates one at a time, ~2–3 min each — the throughput ceiling for two dispatchers per branch.

We solve: rank techs on distance, familiarity, time-to-free and job priority; push an accept/decline offer and cascade automatically. Pure rules and math — no LLM — so every assignment is explainable.

B AI · tech overrides

Job Summarisation Copilot — changing the job status

Mobile · Technician at end of job

Every job's mandatory closeout means 10–15 min of forms and two free-text notes — done properly. In practice ~40% of notes end up ≤40 characters.

We solve: restructure the tech's rough words into a clean note for customer and office, and suggest form values from similar past jobs. Never fabricates, never blocks Save. Target: 10–15 min → ~15 s.

C AI · tech overrides

Technician Parts Finder — finding the part that isn't on the truck

Mobile · Technician on-site

When the first three sources (truck, nearby techs, warehouse) come up empty, the fourth is a phone call to a supplier who may not answer — billable hours burned, or a second truck roll.

We solve: AI suggests the likely part from the problem and equipment; one search shows where it is across all four sources. The tech decides where to pick it up — no price ranking, no ordering.

Work order in → (A) the right tech is offered the job on the web portal → tech arrives on site → (C) the missing part is found on mobile without a phone call → (B) the closeout note writes itself. Full step-by-step diagrams for all three: see §5 Operational Flows.

Cloud placement: the existing FieldJetX platform and all new infra run on Azure; the SQL Server system of record stays on AWS (sole cross-cloud dependency). This restates the existing-platform cloud from the per-use-case docs, which describe the existing platform as running on AWS EC2.

Tracks incoming dispatch requests per division. Durable buffer between Server A and the Container Apps workers.

Distributed per-division lock. Guarantees sequential, non-parallel processing — no two workers touch the same division at once.

Per-technician reply channel. Azure VM API LPUSHes the Accept/Reject; the worker BLPOPs it — instant wake, no polling. EXPIRE 60s self-cleans.

⚠ Fault Tolerance — PEL Expiration & Dual-Execution Shield New

If Task C2 crashes or processing exceeds the visibility timeout, its message stays unacknowledged in the Pending Entries List (PEL):

  1. Surviving worker (e.g. C1) claims the stuck message via XCLAIM
  2. C1 must first acquire lock:div:Div_A before running the flow
  3. Guardrail: if C2 was merely slow (not dead), the live lock blocks C1 → prevents dual execution. If C2 truly died, the lock expires and C1 safely takes over.

Net effect: exactly-once dispatch to technicians — no duplicate assignments, even under crashes or stalls.

Cross-cloud dependency: the Azure VM (.NET API host) and both new Azure Container Apps tiers — Auto-Dispatch workers and the FastAPI AI server — all read and write the same AWS SQL Server database. Until that database itself migrates, every one of those calls crosses a cloud boundary:
  • Network path: target state is a site-to-site VPN or VNet-to-VPC private peering between the Azure subscription and the AWS VPC; until that's provisioned, the fallback is a public SQL Server endpoint locked down by IP allow-listing and TLS 1.2+.
  • Added latency: every dispatch read/write (A) and every ai.* read/write (B, C) pays inter-cloud round-trip time on top of same-region latency — this has to be budgeted into the P95 targets in §9 Observability & Evals, especially for the Auto-Dispatch worker loop's per-request SQL calls.
  • Cost: AWS bills egress on data leaving the VPC toward Azure on every query; that cross-cloud data-transfer line scales with dispatch/summary/parts-lookup volume and belongs in §10 Cost Projection alongside compute.
  • Single seam: this database is the only place Stream 1 still touches AWS — everything else in this section is Azure or on-prem. If the link goes down, all three use cases fall back to their existing manual path (phone-dispatch, forms without AI assist, no parts search) rather than failing silently.

6. Core Logic (per use case)

The algorithms and pipelines behind the flows in §5, lifted at full fidelity — every formula, weight, table and worked example intact, not condensed: how A ranks a shortlist of technicians, how B turns wizard answers into a 12-section ticket (plus the deterministic retrieval and measured baseline it stands on), and how C predicts parts by retrieval and sources them across three tiers.

A Auto-Dispatch — Ranking Algorithm

This is the detail behind step 3 (“Rank the technicians”) of the assignment loop in §5. It turns each candidate's availability, distance, and visit history into a single ordered shortlist. One formula covers every case — its behavior is tuned by a single weight w chosen from the job's dispatch type. Adapted from system-design.html §8 Ranking Algorithm.

Inputs

  • freei — minutes until technician i is available (time left on current job)
  • disti — miles from technician i to the jobsite
  • visitsi — prior visits by technician i to this customer (familiarity)
  • AVG_SPEED — average truck speed in mph, a configurable constant
  • dispatchType — Emergency · High Priority · Medium Priority
↓

Step A — unify availability + distance into one ETA

Distance can't be compared to wait-time directly. Convert distance to travel time using the average truck speed, then add the wait, so every technician collapses to one number: minutes-until-on-site. Lower is better.

travel_i = (dist_i / AVG_SPEED) * 60      # miles -> minutes
eta_i    = free_i + travel_i              # total minutes until tech is on site
↓

Step B — weighted score

Blend ETA and visit count into one score. Both must be on a 0–1 scale where higher is better, so min-max normalize each across this candidate set, then weight by w (the speed share). A pure ranking is just an endpoint: w=1 sorts by ETA only, w=0 by visits only — no separate sort needed.

speed_score_i = (eta_max - eta_i)      / (eta_max - eta_min)      # lowest eta  -> 1.0
fam_score_i   = (visits_i - visits_min)/ (visits_max - visits_min) # most visits -> 1.0

score_i = w * speed_score_i + (1 - w) * fam_score_i               # w = speed weight
# sort score_i descending -> rank 1 = offer target

Edge cases: a single candidate is rank 1 by default; if all ETAs tie the speed term is flat and familiarity breaks the tie (and vice-versa).

↓

Step C — pick w from the dispatch type

Emergency and Medium are just the two ends (w=1, w=0) of the same combined formula — so one code path serves all three.

Dispatch TypeStrategyw (speed)Result
EmergencySpeed-Based (locked)1.0Pure ETA; familiarity ignored — lowest combined time wins
High PriorityCombined0.2 (Speed 20 / Fam 80)Weighted blend; weight configurable per strategy
Medium PriorityFamiliarity-Based0.0Pure visit count — most familiar tech wins
One formula, three behaviors: the dispatch type only sets w. Emergency (w=1) reduces to pure speed, Medium (w=0) to pure familiarity, High blends them — no separate ranking code per type. The resulting ordered shortlist feeds directly into step 4 (offer to the top-ranked technician) in §5.
Future factor — skill gate: when technician skill data is available (1 ≤ skilli ≤ 5) and a job carries a minimum required skill, it enters as a hard gate, not a score term. Filter it in step 1 when building the candidate list — keep technician i only if skilli ≥ job.minSkill — so under-skilled technicians never reach ranking. The speed/familiarity scoring is untouched; only the candidate set shrinks.

B Job Summarisation — Summarise Pipeline & Retrieval

The 12-section ticket followed end to end, plus the retrieval mechanics and measured baseline it stands on. Adapted from usecase-b-architecture.html §10 The Summarise Pipeline and §12 Retrieval, Suggestions & the Measured Baseline.

The Summarise Pipeline

One request followed end to end: what happens between the technician reaching the Review step and the 12-section ticket appearing.

1

Mobile app compiles the payload

The wizard answers (reason, parts, time, notes, completed forms, dropdowns decoded to labels) are packed client-side with zero extra API calls, then sent as POST /api/v1/summarise with the app's existing auth token.

2

.NET proxy validates & forwards

The Microservices API validates the OAuth2/Entra token, strips user credentials, adds the internal API key, and forwards server-to-server to the private FastAPI service with an extended timeout.

3

Parallel enrichment (fail-soft)

Three reads fire simultaneously against the existing APIs: dispatch details (GetAssignedDispatchesDetails), per-equipment fields (GetDispatchEquipmentFieldData), and customer procedures (GetDispatchProcedures, always fetched live, never cached). If any fetch fails, the pipeline continues without it.

4

Prompt construction

A versioned ticket standard (ticket_standard.md) forms the system instruction; the user prompt assembles dispatch context, equipment specs, completed forms, wizard answers, and procedures. Token profile ≈ 2,080 in / 1,050 out per dispatch.

5

LLM call to the client's own model

The pipeline calls qwen3-vl on the client's private gateway (measured ~6–7s per call, 30–35 tok/s; data never leaves client infrastructure). The provider abstraction in llm_client.py stays, so a different model can be swapped in by config later, but no external provider is wired up. Returns the raw ticket + procedure checks as JSON.

6

Parse, guarantee, post-process

The response is parsed and normalised against the canonical 12-section list: absent sections get an explicit MISSING placeholder, so the app always receives exactly 12 sections in standard order. Deterministic Python overrides then apply wizard-type rules (e.g. Sign-Off rebuilt from the last time entry; Refrigerant Tracking set N/A when no refrigerant was used).

7

Review, fix gaps, submit

The technician sees the ticket with per-section status badges and the procedure checklist; critical gaps must be fixed inline before submit. Submission then flows through the existing mobile-post write-back unchanged, and the accepted summary is persisted to ai.summaries.

How retrieval works

Everything the copilot retrieves is deterministic SQL over the client's real dispatch history: explainable, zero new infrastructure, and already measured against a full year of staging data (252,615 dispatches). This is what replaced the earlier vector-index plan after the 2026-07-07 architecture call.

NeedMechanism
Same-site history (briefing)Keyed SQL query: past visit digests for the same customer and site, most recent first.
Similar past issues (briefing)Deterministic lookup: 2–3 recent dispatches with the same equipment type and problem code are pulled and handed to the LLM as context. No embeddings, no similarity index.
Part suggestionsSQL co-occurrence: a frequency table keyed on (equipment manufacturer type × problem code) → most-used parts, with fallback to equipment type alone, then global top parts. One SQL aggregation, fully explainable.
Compliance proceduresAlways fetched live from the source system, never cached or embedded: they are compliance-critical and change.

The measured baseline (backtested on staging, 2026-07-08)

The co-occurrence method was trained on 11 months of real dispatches and tested on the final month (4,151 dispatches with installed parts, 3,100 distinct parts in play). “Hit” means at least one actually-installed part appeared in the top-k suggestion list:

Why this matters: with 3,100 possible parts, a zero-ML lookup already puts a right part in a 5-item list 40% of the time. This is the baseline any classical-ML model, embedding index, or LLM-heavy approach must beat to justify its added cost and complexity, exactly the “capture the baseline, commit to no accuracy numbers” framing agreed on the call.

Label-quality reality (what the EDA must account for)

An audit of the last 12 months of staging data showed the structured outcome codes are far weaker than they look: root-cause and failure codes have been dead since 2021, the problem code's top value is OTHER at 38%, and the summary code is SERVICE for 88% of filled rows. The genuine predictive signal lives in the free-text complaint (DispatchReason, 230k+ distinct values) and technician notes, plus equipment identity. Any classical-ML phase therefore must include text feature engineering; training on code columns alone will underperform the baseline above.

C Parts Finder — Matching & Sourcing Logic

Prediction is retrieval-augmented: find the most similar past dispatches, then rank the parts those dispatches used, weighting closeness over raw frequency so one near-identical job outranks several loosely-similar ones. Once parts are identified, the Source API works out where to get them from. Adapted from usecase-C-system-design.html §7 RAG Prediction & Ranking and §8 Sourcing Algorithm.

Pipeline

  1. Asymmetric embedding. Historical reasons are embedded at index time with a document task type; the live dispatch reason is embedded per request with a query task type. Both run on the self-hosted embedding model on customer hardware — dispatch text never goes to an external AI provider.
  2. Retrieve. Search the Azure-hosted vector store for the top K = 15 nearest neighbors, returning cosine distances and each neighbor's partsUsed.
  3. Rank & aggregate. The self-hosted LLM ranks & aggregates the retrieved parts: convert distance to similarity, gate on a threshold, and accumulate a cubed-similarity score per part.
  4. Confidence & select. Normalize scores, clamp to a confidence band, return the top parts, and pre-select the confident ones.

Scoring (exact)

sim            = 1 − cosine_distance
if sim > 0.55:                      # SIM_THRESHOLD — neighbor contributes
    for part in neighbor.partsUsed:
        score[part]     += sim ** 3      # closeness > frequency
        timesUsed[part] += 1

confidence(part) = clamp( round( score[part] / max_score × 95 ), 20, 95 )

return top 6 parts by score              # each pre-selected if confidence ≥ 60

The response also reports basedOn — the number of neighbors above threshold — so the client can convey how much history a prediction rests on.

Indexing & the self-learning loop

  • Idempotent upsert keyed by dispatchNo: only dispatches not already indexed are embedded, so re-runs and restarts are cheap.
  • Rate-limit-aware batching: embeddings are computed in batches with pacing and retry-with-backoff on throttling.
  • Feedback loop: when a dispatch is marked complete in SQL Server, its reason and used parts are embedded and upserted — the very next similar job benefits (the dashed learning-loop arrow in the architecture diagram in §2).

Ordering & allocation

  • Sort: truck first (0 mi), then all other sources by ascending distance — closest picked first.
  • Pricing: own stock (truck + warehouse) has no price; only the United vendor tier carries a dollar cost, applied from InventorySupplierXREF.currentcost.
  • Split large needs: per-source quantities are limited, so a large requested quantity is spread across sources. The client allocates greedily down the sorted list — each source takes min(remaining_need, available) until the need is met.
# greedy allocation across the sorted sources
remaining = qtyNeeded
for src in sources:            # truck first, then nearest → furthest
    take        = min(remaining, src.available)
    src.taken   = take
    remaining  -= take
    if remaining == 0: break
Vendor lookup fails → drop the tier, not the request. If the vendor lookup fails, the vendor tier is dropped rather than failing the whole request — the technician still sees all own-stock options. See §11 Onboarding & Fault Tolerance.

A Auto-Dispatch — Azure Cache for Redis Data Structures

The three Redis structures that coordinate dispatch across the Container Apps worker pool. Adapted from system-design.html §6 Redis Data Structures.

StructureKeyPurpose
STREAMdispatch:streamDurable buffer of incoming dispatch requests between Server A and the Container Apps workers. Consumed via a consumer group (XREADGROUP) — all N workers compete; each message goes to exactly one worker.
MUTEXlock:tech:{techId}Per-technician distributed lock. A request acquires locks on its candidate technicians before offering, in a fixed order (e.g. ascending techId) to avoid deadlock between overlapping requests. Requests with disjoint candidates run in parallel — even in the same division; requests sharing a technician serialize on that lock, so a tech is never double-offered. TTL self-releases on a crashed worker.
LISTresp:{dispatchId}:{techId}Per-technician reply channel. The Azure VM API LPUSHes the Accept/Reject; the worker BLPOPs it — instant wake, no polling. EXPIRE 60s self-cleans.
Concurrency: a worker processes up to 20 dispatches concurrently using async (redis.asyncio) — a blocked BLPOP on one dispatch never stalls the others.

Vector store — dispatch-parts index Azure

Each historical completed dispatch becomes one record, indexed for cosine similarity:

# one record per completed dispatch
id        = dispatchNo                 # stable key → idempotent upsert
document  = dispatch.reason            # the embedded text
embedding = embed(reason, DOCUMENT)    # vector (cosine / HNSW)
metadata  = { partsUsed: [ {partNo, qty}, ... ] }
Derived, not authoritative: the vector store holds only the reason text and the parts that were actually used. It is a derived, rebuildable index — the relational database remains the system of record.

A Auto-Dispatch — API Reference

New endpoints introduced for Auto-Dispatch. Two callers: the admin dashboard (control plane — toggle & config) and the technician mobile app (data plane — push registration & replies). All existing endpoints (dispatch ingestion, dispatch status, technician location) are unchanged and out of scope here. Adapted from system-design.html §9 API Reference.

MethodPathCallerPurpose
POST/divisions/{id}/toggleDashboard → Azure VMTurn auto-dispatch ON/OFF for one division. Body { enabled: bool }. On enable: pull pending requests into the stream and scale the Container Apps pool up; on disable: drain and scale to zero (idle = $0).
PUT/divisions/{id}/configDashboard → Azure VMUpdate per-division ranking weights — distance, familiarity, priority, availability window. Body { weights: {...} }. Applied to the next assignment loop; no restart needed.
GET/divisions/{id}/configDashboard → Azure VMRead current toggle state + weights so the admin UI can render the switch position and weight sliders. Paired read for the two writes above.
POST/devices/registerMobile → Azure VMRegister/refresh a device push token. Body { techId, platform: ios|android, token }. Azure VM registers the device with Notification Hubs and stores techId → deviceInstallationId. Re-posted whenever the OS rotates the token, so pushes never silently die.
POST/technicians/{id}/availabilityMobile → Azure VMTechnician reports when they will be free. Body { availableAt }. Not tied to any dispatch — it updates the technician's general availability state, which the ranking loop reads for whichever request is being processed.

Authentication

No new auth mechanism is introduced. Every endpoint sits behind the platform's existing auth middleware, by caller:

  • Control plane (POST /divisions/{id}/toggle, PUT /divisions/{id}/config, GET /divisions/{id}/config) — behind the admin Dashboard auth, identical to the existing Dashboard endpoints. Only authenticated admins can toggle or reconfigure a division.
  • Data plane (POST /devices/register, POST /technicians/{id}/availability, POST /dispatches/{id}/respond) — behind the technician mobile-app auth, identical to the existing technician endpoints. The authenticated technician identity must match the techId/technician in the path or body.

Error contract

All endpoints return the platform's standard error envelope so a client can handle failures uniformly:

{ "code": "string",        // stable machine code, e.g. DIVISION_NOT_FOUND
  "message": "string",     // human-readable
  "requestId": "string" }  // correlation id for tracing

Global status codes apply across all endpoints:

  • 400 — malformed body / invalid field (e.g. weight out of range, unknown platform).
  • 401 — missing/invalid credentials · 403 — authenticated but not permitted (e.g. non-admin hitting a control-plane route, technician acting for another techId).
  • 404 — division / dispatch / technician not found.
  • 409 — duplicate reply on /dispatches/{id}/respond (the SETNX dedupe already rejected it); the first reply stands.
  • 500 — unexpected server error (correlate via requestId).

Two response types — two separate endpoints

The technician's two replies live at different paths because they have different scope:

  • Availability — POST /technicians/{id}/availability. Tech-scoped, no dispatchId. A general "I'm free at …" answer to the availability poll during the ~1 min ranking window; updates the technician's availability record that ranking reads.
  • Decision — POST /dispatches/{id}/respond. Dispatch-scoped. Accept/reject one specific offer; drives the offer loop, and a reject (or timeout) moves to the next ranked technician. This is the reply the worker is blocked on (BLPOP).
