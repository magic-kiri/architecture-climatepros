High-Level Design
01 · Overview

01System Overview

The Technician Parts Finder adds two capabilities to the FieldJetX FJX 2.2 mobile app used by field technicians: predicting the parts a dispatch is likely to need from the dispatch's written reason, and sourcing each part across every place it can be gathered — the tech's own van, other Climate Pros warehouses, the branch warehouse, and the nearest United Refrigeration vendor branch.

Core principle: the system learns from its own history. Every completed dispatch in the system of record feeds a retrieval index, so predictions improve as more work is done — no manual rules to maintain. Prediction is additive and advisory: the technician stays in control and can always add parts manually.

🔮
RAG Prediction

Embed the dispatch reason, retrieve the most similar past jobs, and rank the parts those jobs actually used.

📦
Multi-Source Gather

For every part, surface all stock locations — own inventory first (free), vendor last (priced).

🔁
Self-Learning Loop

Completed dispatches are re-embedded and upserted into the vector store, closing the feedback loop automatically.

✍️
Manual Fallback

If prediction is unavailable, the technician adds parts from inventory search — the flow never blocks.

02 · Motivation

02Problem & Goals

Current bottleneck. A technician reads a dispatch, guesses which parts the repair will require from experience, and then hunts for those parts across their van, nearby warehouses, and vendor counters. Wrong guesses mean second trips; blind sourcing means driving further than necessary or paying a vendor for something already sitting in a colleague's van.

Goals

GoalWhat it means
Predict from historyTurn the free-text dispatch reason into a ranked, confidence-scored list of likely parts, grounded in what similar past jobs actually used.
Source everywhereFor each part, show every place it can be gathered, ordered so the cheapest/closest option is picked first.
Minimize trips & costPrefer the tech's own stock (free) over other warehouses, and warehouses over the priced vendor branch.
Stay in the existing appDeliver entirely inside FJX 2.2 — no new app for the technician to learn or install.
Improve automaticallyEvery completed dispatch makes the next prediction better, with no rule maintenance.

Success metric

Reduction in parts-driven return trips per dispatch, and the share of predicted parts the technician accepts (prediction acceptance rate).

Non-goals

  • Replacing technician judgment — predictions are suggestions, never auto-committed.
  • Automatic purchasing or PO creation from the vendor (a future improvement).
  • Warehouse/inventory management — stock levels remain owned by the system of record.

04 · Architecture

04High-Level Architecture

Three zones: the existing FieldJetX platform stays unchanged, the new AI layer runs in a private AWS VPC, and the models are self-hosted on customer hardware. The technician triggers the flow from FJX 2.2; the .NET Microservices API proxies to the FastAPI AI Server, which orchestrates retrieval, ranking, and multi-source gathering — and every completed dispatch feeds back into the index.

Request flow

  1. Technician taps "Add parts" on a dispatch in FieldJetX (FJX 2.2) — the app talks to the existing .NET APIs, exactly as it does today (step 1).
  2. The .NET Microservices API's new AI proxy route forwards the Predict / Source call to the FastAPI AI Server (ECS Fargate) (step 2).
  3. The AI server reads the dispatch reason and stock context from the .NET Legacy API (step 3).
  4. The dispatch reason is embedded by the self-hosted embedding model on customer hardware.
  5. The query vector is searched against the Vector DB (Amazon S3 Vectors) and the nearest past dispatches are retrieved (RAG) (step 4).
  6. The self-hosted LLM ranks & aggregates the parts those jobs used and the result returns to the technician (step 5).
  7. The Source API gathers own-stock per part from SQL Server and persists the parts list into the new ai.* schema (step 6); the supplier tier is fetched server-side from the United Refrigeration CP Gateway (outside the diagram's numbered path).
  8. All calls are traced to CloudWatch + ADOT.
  9. When a dispatch is later marked complete in SQL Server, its reason + parts are re-embedded and upserted into the Vector DB — closing the learning loop.

Core Design
06 · Data

06Data Model

Two stores cooperate: the relational system of record (SQL Server fieldgetics) owns dispatches, inventory, and stock; the vector store (Amazon S3 Vectors) holds the semantic index used for prediction. AI-written data lands in a new ai.* schema in the same SQL Server — clear isolation from the existing tables.

System of record — fieldgetics (SQL Server)

EntityKey fields usedPurpose in this system
Dispatchreason, problemCode, repairCategory, priority, nte, branchWarehouseThe reason text is the prediction input; completion feeds the learning loop.
DispatchPartsRequest / Inventorypart number, name, categoryParts catalog and the parts a dispatch requests/uses.
InventoryLocationXreflocation, quantity-on-hand Stock by location — drives own-stock (truck + warehouse) availability in sourcing.
InventorySupplierXREFcurrentcost Vendor price for a part (the United API returns stock + location; price is applied from here).

New ai.* schema — AI-owned relational data

Everything the AI layer writes to SQL Server lives in its own schema: the parts lists a technician commits (with per-source allocations), prediction acceptance signals, and indexing bookkeeping. Nothing in the existing dbo tables changes — the AI footprint can be audited, backed up, or dropped independently.

Vector store — dispatch-parts index (Amazon S3 Vectors)

Each historical completed dispatch becomes one record, indexed for cosine similarity:

# one record per completed dispatch
id        = dispatchNo                 # stable key → idempotent upsert
document  = dispatch.reason            # the embedded text
embedding = embed(reason, DOCUMENT)    # vector (cosine / HNSW)
metadata  = { partsUsed: [ {partNo, qty}, ... ] }
🗝️

The vector store holds only the reason text and the parts that were actually used. It is a derived, rebuildable index — the relational database remains the system of record.

07 · Algorithm

07RAG Prediction & Ranking

Prediction is retrieval-augmented: find the most similar past dispatches, then rank the parts those dispatches used, weighting closeness over raw frequency so one near-identical job outranks several loosely-similar ones.

Pipeline

  1. Asymmetric embedding. Historical reasons are embedded at index time with a document task type; the live dispatch reason is embedded per request with a query task type. Both run on the self-hosted embedding model on customer hardware — dispatch text never goes to an external AI provider.
  2. Retrieve. Search the vector store (Amazon S3 Vectors) for the top K = 15 nearest neighbors, returning cosine distances and each neighbor's partsUsed.
  3. Rank & aggregate. The self-hosted LLM ranks & aggregates the retrieved parts: convert distance to similarity, gate on a threshold, and accumulate a cubed-similarity score per part.
  4. Confidence & select. Normalize scores, clamp to a confidence band, return the top parts, and pre-select the confident ones.

Scoring (exact)

sim            = 1 − cosine_distance
if sim > 0.55:                      # SIM_THRESHOLD — neighbor contributes
    for part in neighbor.partsUsed:
        score[part]     += sim ** 3      # closeness > frequency
        timesUsed[part] += 1

confidence(part) = clamp( round( score[part] / max_score × 95 ), 20, 95 )

return top 6 parts by score              # each pre-selected if confidence ≥ 60
ConstantValueEffect
TOP_K15Neighbors retrieved per query.
SIM_THRESHOLD0.55A neighbor contributes only if sim > 0.55; weaker matches are ignored.
Weightsim³Cubed similarity — sharply favors very close matches.
Confidence band[20, 95]Normalized to the top score × 95, then clamped.
Output sizeTop 6Highest-scoring parts returned to the technician.
CONFIDENCE_THRESHOLD60Parts with confidence ≥ 60 are pre-selected in the UI; the rest are shown unchecked.

The response also reports basedOn — the number of neighbors above threshold — so the client can convey how much history a prediction rests on.

Indexing & the self-learning loop

  • Idempotent upsert keyed by dispatchNo: only dispatches not already indexed are embedded, so re-runs and restarts are cheap.
  • Rate-limit-aware batching: embeddings are computed in batches with pacing and retry-with-backoff on throttling.
  • Feedback loop: when a dispatch is marked complete in SQL Server, its reason and used parts are embedded and upserted — the very next similar job benefits (the dashed learning-loop arrow in the architecture diagram).
08 · Algorithm

08Sourcing Algorithm

For each requested part, the Source API returns every place the part can be gathered, ordered so the technician takes the cheapest, closest stock first and only falls back to the priced vendor when needed.

Source tiers

TierWhat it isDistancePrice
truckThe technician's own van inventory. 0 mifree
warehouseOther Climate Pros warehouses — including other technicians' vans — plus the branch warehouse.by distance, nearest firstfree
vendorThe nearest United Refrigeration branch — the outside parts supplier (CP API Gateway).from gateway priced
🚐

A van is a warehouse. Per operations, there is no separate "nearby technician" tier — another tech's van is modeled as a warehouse (labeled with the person's name, a warehouse code, and a street address). This keeps the model simple and reflects how stock actually moves in the field.

Ordering & allocation

  • Sort: truck first (0 mi), then all other sources by ascending distance — closest picked first.
  • Pricing: own stock (truck + warehouse) has no price; only the United vendor tier carries a dollar cost, applied from InventorySupplierXREF.currentcost.
  • Split large needs: per-source quantities are limited, so a large requested quantity is spread across sources. The client allocates greedily down the sorted list — each source takes min(remaining_need, available) until the need is met.
# greedy allocation across the sorted sources
remaining = qtyNeeded
for src in sources:            # truck first, then nearest → furthest
    take        = min(remaining, src.available)
    src.taken   = take
    remaining  -= take
    if remaining == 0: break
⚠️

If the vendor lookup fails, the vendor tier is dropped rather than failing the whole request — the technician still sees all own-stock options. See Fault Tolerance.

09 · Interface

09API Reference

The FastAPI AI Server exposes a deliberately small HTTP surface, reached by FJX 2.2 through the .NET Microservices API's AI proxy route — the mobile app never calls the AI layer directly, and the proxy forwards exactly the two control endpoints (/parts/predict, /parts/source).

EndpointPurpose
GET /healthLiveness / deploy probe (load-balancer + ECS health checks; not proxied to clients).
POST /parts/predictRAG-predicted parts for a dispatch — via the AI proxy route.
POST /parts/sourceAll sources per part — via the AI proxy route.
ℹ️

Everything else the flow touches stays where it already lives: dispatch list/detail and the manual-add inventory tabs / catalog search are served by the existing .NET APIs, unchanged. The AI server does not serve or duplicate them — it reads the dispatch reason and stock context from the Legacy API (diagram step 3), and calls the United CP Gateway server-side for the supplier tier.

POST /parts/predict

// request
{ "dispatchId": "..." }

// response → PredictedPart[]
[ {
  "inventoryId": "C066",
  "name":        "Condenser Fan Motor 1/4 HP",
  "partNumber":  "C066",
  "confidence":  88,          // 20–95
  "selected":    true,        // pre-selected when confidence ≥ 60
  "timesUsed":   3
} ]

10 · Client

10Client Flow (FJX 2.2 mobile)

The experience lives inside FieldJetX (Flutter · Cupertino, brand #114D9A, Lucide icons — consistent with the FieldJetX/Symphony theme). From a dispatch, the technician moves through a short parts flow: dispatch → add parts → source → confirm.

🔮 Add Parts with AI

Calls /parts/predict and merges results into the current list, de-duplicated by inventoryId — prediction is additive, never a replacement. Confident parts arrive pre-selected.

✍️ Add from Inventory

Manual search over inventory tabs (truck / all / cons / customer) and catalog; selected items merge into the same list with the same de-dupe rule.

📦 Source & allocate

Calls /parts/source, then a per-part Need stepper drives greedy allocation across the sorted sources; the quantity is clamped to total availability.

✅ Confirm

A summary shows each part and exactly which sources it will be taken from (own stock highlighted, vendor flagged) before the technician commits.

Behavior details

  • Additive merge, dedupe by inventoryId: AI and manual adds never overwrite an existing entry; a part already on the list keeps its quantity.
  • Per-dispatch persistence: each dispatch's parts list is retained, so re-opening a dispatch restores its work in progress.
  • AI vs manual signalling: a part's confidence distinguishes an AI suggestion from a manually added part in the UI.
  • Greedy re-allocation: changing the Need count re-fills the allocation across sources immediately, clamped to what's available.
11 · Observability

11Observability & Tracing

Every predict, source, and vendor call is traced end-to-end with AWS CloudWatch + ADOT (the AWS Distro for OpenTelemetry), so latency and failures are attributable to a specific stage.

🧭
Traces

One span tree per request: proxy → embed → vector search → rank, and per-part fan-out to SQL Server / United.

📊
Metrics

Prediction latency (including the self-hosted model hops), neighbors above threshold (basedOn), supplier-lookup success rate, and the source mix (truck / warehouse / vendor).

🪵
Logs

Structured request logs correlated by trace id; no raw customer PII in log bodies.

Alarms fire on elevated error rate or p95 latency; the /health endpoint backs load-balancer and deployment health checks.

12 · Operations

12Deployment & Rollout

The FastAPI AI Server ships as a container image to ECS Fargate in a private AWS VPC, bound to an injected $PORT, with the vector index seeded from historical completed dispatches before go-live. The mobile app needs no release for the backend rollout — it reaches the AI layer through the .NET Microservices API's proxy route.

Phase 0 — Provision

  • ECS Fargate service (private VPC) + internal load balancer; container image built in CI.
  • Amazon S3 Vectors bucket + index created; connectivity to the customer-hosted embedding model and LLM configured and health-checked.
  • Network path + credentials to SQL Server (reads + the new ai.* schema), the .NET Legacy API, and the United CP Gateway.
  • ai.* schema migration applied to SQL Server; AI proxy route deployed on the .NET Microservices API.

Phase 1 — Seed the index

  • Batch-embed historical completed dispatches on the self-hosted embedding model (idempotent upsert by dispatchNo).
  • Validate retrieval quality on a held-out set of recent dispatches.

Phase 2 — Client rollout

  • Ship the "Add Parts with AI" / sourcing experience in FJX 2.2 behind a feature flag, enabled per branch/division.
  • Pilot with a small technician cohort; watch acceptance rate and source mix.

Phase 3 — Go-live & continuous learning

  • Expand the flag division-by-division.
  • Wire the on-completion re-embed pipeline so the index grows automatically.

13 · Security

13Security & PII

AreaControl
Client → service authBearer token from the FJX 2.2 session, validated at the .NET Microservices API before the AI proxy route forwards the call; CORS restricted to the mobile client.
Network isolationThe AI layer runs in a private AWS VPC — the FastAPI AI Server is not internet-reachable; only the .NET proxy route (and the VPC paths to SQL Server, S3 Vectors, and the customer-hosted models) can reach it.
Model hostingEmbedding and LLM inference run on client-provided, self-hosted models on customer hardware — dispatch text and parts history are never sent to a third-party AI provider.
Supplier gatewayUnited calls carry the Ocp-Apim-Subscription-Key header; the key is held server-side only and never reaches the mobile client.
Secrets managementAll credentials (gateway key, DB, model endpoints) resolved from a secret store — AWS Secrets Manager / SSM Parameter Store — with rotation. No secrets in source or images.
Data store accessLeast-privilege SQL Server account: read-scoped on inventory and dispatch tables, write access confined to the new ai.* schema; network-restricted to the service subnet.
TransportTLS on all hops (client, proxy, gateway, model endpoints, internal service calls).

PII inventory

  • Dispatch & customer detail (name, address, phone) — served to the authenticated technician only; excluded from log bodies.
  • Van / warehouse locations — used transiently for distance ordering; not persisted beyond short-lived caching.
  • The vector store (S3 Vectors) holds no direct customer PII — only dispatch reason text and used part numbers — reducing the sensitivity of the derived index.
🔐

Because the vector index is derived and rebuildable, it can be re-seeded from the system of record at any time — supporting deletion and data-retention requests handled at the SQL Server layer.

14 · Reliability

14Fault Tolerance & Reliability

The system is designed to degrade gracefully — no single dependency can block a technician from adding and sourcing parts.

FailureBehavior
Self-hosted models / vector store unavailable/parts/predict returns 503; the client falls back to manual inventory add — the flow continues.
Supplier (United) outageThe vendor tier is dropped from a part's sources; own-stock options are still returned. The request does not fail.
Model throttling / slownessRetry with backoff and batched pacing at index time; request-time timeouts bound prediction latency. Transient throttling doesn't corrupt the index.
Duplicate / repeated indexingIdempotent upsert keyed by dispatchNo — re-running indexing never double-counts a dispatch.
SQL Server slow / unavailableRead replicas + brief caching for hot stock lookups; sourcing surfaces last-known availability where safe.
Service task crashStateless Fargate tasks behind the load balancer; ECS service scheduling replaces unhealthy tasks (health-checked via /health).

15Cost Projection

Cost splits into a fixed AWS infrastructure baseline and a variable per-prediction component. Because the embedding model and LLM are self-hosted on customer hardware, there is no per-token model fee in this budget — the models' cost is the client's hardware, outside this projection. 16 · Roadmap

16Future Improvements

🎓 Skill / certification gating

Filter or flag predicted parts by the technician's certifications and the equipment on the dispatch.

🔁 Feedback / reward loop

Learn from which suggested parts the technician actually used vs. dismissed, feeding acceptance signals back into ranking.

📈 Beyond new requests

Extend prediction to follow-up visits and preventive-maintenance dispatches, not just brand-new service calls.

🛒 Assisted ordering

One-tap vendor purchase/reservation from the United gateway when own stock can't cover the need.

🌎 Multi-region scaling

Per-division indices and vendor branch sets as the capability rolls out beyond the initial region.

⏱️ Real-time stock

Tighter live inventory sync so allocation reflects stock committed by other in-flight dispatches.
