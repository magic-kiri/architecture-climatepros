Auto-Dispatch

System Design — Use Case A (HLD & LLD)

An admin toggle drives fully automated, division-isolated technician dispatch — layered on the existing EC2 + RDS application, with a new Redis (ElastiCache) + AWS Fargate processing tier for concurrency, fault tolerance, and scale-to-zero cost control, plus an Amazon SNS round-trip for real-time technician notify & reply.

Toggle → automated dispatch| Division-isolated · exactly-once| July 2026

1. System Overview

Auto-Dispatch turns manual technician assignment into a fully automated pipeline. An admin flips a per-division toggle; from then on every new dispatch request for that division is picked up, routed to the nearest available technicians, and assigned — with no operator in the loop. When the toggle is OFF the processing tier scales to zero, so an idle division costs nothing.

⚙

Core principle: toggle-driven, division-isolated, zero-cost-idle

One admin switch per division. Automation runs on a scale-to-zero Fargate pool; divisions never interfere with each other.

Dispatch requests flow through a durable Redis Stream into a pool of competing Fargate workers. A per-division distributed lock guarantees one division is processed sequentially — never in parallel — so two workers can never double-assign the same job. Technician replies arrive over an SNS → phone → EC2 → Redis round-trip that a worker wakes on instantly via BLPOP (no polling).

2. Problem & Goals

Today an admin hand-picks a technician for every dispatch request. That does not scale: it is slow, serial, blind to who is actually nearest and available, and has no parallelism across divisions. As request volume grows the admin becomes the bottleneck.

⚠

Goals & invariants

What the automated system must guarantee.

  • Exactly-once dispatch — a request is assigned to exactly one technician, even under worker crashes or stalls.
  • Conflict-aware concurrency — two requests run in parallel when their candidate technicians are disjoint (even within the same division); they serialize only when they share a common technician, so a tech is never double-offered or double-assigned.
  • No-polling reply — technician Accept/Reject wakes the worker instantly.
  • Scale-to-zero — a disabled or idle division consumes no compute.
📊

Success metric

How we know the automation is working, not just running.

  • Escalation-to-human rate ≤ Y% — share of dispatches that exhaust the ranked shortlist (every candidate timed out or rejected) and fall back to a human. This is the automation's failure-to-automate ceiling: a low, stable rate means auto-dispatch is actually placing jobs; a rising rate signals bad ranking, thin technician coverage, or low reply adoption. Target Y is set from the single-division pilot baseline (Section 11) before full rollout.
Non-goals: the existing manual dispatch flow is untouched — a division with the toggle OFF behaves exactly as today. No UI change beyond the toggle and its configuration (task count N). No change to the RDS system of record schema beyond dispatch status fields.

4. High-Level Architecture

Request Flow

  1. Dashboard sends the dispatch request to .NET Legacy API; toggle + config (N) to .NET Microservices API.
  2. If the division is ENABLED, .NET Legacy API publishes the dispatch id to dispatch:stream.
  3. .NET Microservices API (via boto3) scales the Fargate pool to N on enable, to 0 on disable.
  4. A Fargate worker XREADGROUPs the message, locks its candidate technicians (lock:tech:{id}), and runs the assignment flow.
  5. The worker notifies technicians via SNS and blocks on a per-tech Redis list (BLPOP) for the reply.
  6. On assignment the worker writes to RDS, releases the lock, and XACKs the message.

8. Ranking Algorithm

This is the detail behind step 3 ("Rank the technicians") of the assignment loop above. It turns each candidate's availability, distance, and visit history into a single ordered shortlist. One formula covers every case — its behavior is tuned by a single weight w chosen from the job's dispatch type.

Inputs

  • freei — minutes until technician i is available (time left on current job)
  • disti — miles from technician i to the jobsite
  • visitsi — prior visits by technician i to this customer (familiarity)
  • AVG_SPEED — average truck speed in mph, a configurable constant
  • dispatchType — Emergency · High Priority · Medium Priority
↓

Step A — unify availability + distance into one ETA

Distance can't be compared to wait-time directly. Convert distance to travel time using the average truck speed, then add the wait, so every technician collapses to one number: minutes-until-on-site. Lower is better.

travel_i = (dist_i / AVG_SPEED) * 60      # miles -> minutes
eta_i    = free_i + travel_i              # total minutes until tech is on site
↓

Step B — weighted score

Blend ETA and visit count into one score. Both must be on a 0–1 scale where higher is better, so min-max normalize each across this candidate set, then weight by w (the speed share). A pure ranking is just an endpoint: w=1 sorts by ETA only, w=0 by visits only — no separate sort needed.

speed_score_i = (eta_max - eta_i)      / (eta_max - eta_min)      # lowest eta  -> 1.0
fam_score_i   = (visits_i - visits_min)/ (visits_max - visits_min) # most visits -> 1.0

score_i = w * speed_score_i + (1 - w) * fam_score_i               # w = speed weight
# sort score_i descending -> rank 1 = offer target

Edge cases: a single candidate is rank 1 by default; if all ETAs tie the speed term is flat and familiarity breaks the tie (and vice-versa).

↓

Step C — pick w from the dispatch type

Emergency and Medium are just the two ends (w=1, w=0) of the same combined formula — so one code path serves all three.

Dispatch TypeStrategyw (speed)Result
EmergencySpeed-Based (locked)1.0Pure ETA; familiarity ignored — lowest combined time wins
High PriorityCombined0.2 (Speed 20 / Fam 80)Weighted blend; weight configurable per strategy
Medium PriorityFamiliarity-Based0.0Pure visit count — most familiar tech wins
One formula, three behaviors: the dispatch type only sets w. Emergency (w=1) reduces to pure speed, Medium (w=0) to pure familiarity, High blends them — no separate ranking code per type. The resulting ordered shortlist feeds directly into step 4 (offer to the top-ranked technician).
Future factor — skill gate: when technician skill data is available (1 ≤ skilli ≤ 5) and a job carries a minimum required skill, it enters as a hard gate, not a score term. Filter it in step 1 when building the candidate list — keep technician i only if skilli ≥ job.minSkill — so under-skilled technicians never reach ranking. The speed/familiarity scoring is untouched; only the candidate set shrinks.

9. API Reference

New endpoints introduced for Auto-Dispatch. Two callers: the admin dashboard (control plane — toggle & config) and the technician mobile app (data plane — push registration & replies). All existing endpoints (dispatch ingestion, dispatch status, technician location) are unchanged and out of scope here.

MethodPathCallerPurpose
POST /divisions/{id}/toggle Dashboard → EC2 Turn auto-dispatch ON/OFF for one division. Body { enabled: bool }. On enable: pull pending requests into the stream and scale the Fargate pool up; on disable: drain and scale to zero (idle = $0).
PUT /divisions/{id}/config Dashboard → EC2 Update per-division ranking weights — distance, familiarity, priority, availability window. Body { weights: {...} }. Applied to the next assignment loop; no restart needed.
GET /divisions/{id}/config Dashboard → EC2 Read current toggle state + weights so the admin UI can render the switch position and weight sliders. Paired read for the two writes above.
POST /devices/register Mobile → EC2 Register/refresh a device push token. Body { techId, platform: ios|android, token }. EC2 calls SNS CreatePlatformEndpoint and stores techId → endpointArn. Re-posted whenever the OS rotates the token, so pushes never silently die.
POST /technicians/{id}/availability Mobile → EC2 Technician reports when they will be free. Body { availableAt }. Not tied to any dispatch — it updates the technician's general availability state, which the ranking loop reads for whichever request is being processed.
POST /dispatches/{id}/respond Mobile → EC2 Technician accepts/rejects a specific offer. Body { accept: bool }. Deduped via SETNX, then LPUSHed to resp:{dispatchId}:{techId}; the worker's BLPOP wakes instantly.

Authentication

No new auth mechanism is introduced. Every endpoint sits behind the platform's existing auth middleware, by caller:

  • Control plane (POST /divisions/{id}/toggle, PUT /divisions/{id}/config, GET /divisions/{id}/config) — behind the admin Dashboard auth, identical to the existing Dashboard endpoints. Only authenticated admins can toggle or reconfigure a division.
  • Data plane (POST /devices/register, POST /technicians/{id}/availability, POST /dispatches/{id}/respond) — behind the technician mobile-app auth, identical to the existing technician endpoints. The authenticated technician identity must match the techId/technician in the path or body.

Error contract

All endpoints return the platform's standard error envelope so a client can handle failures uniformly:

{ "code": "string",        // stable machine code, e.g. DIVISION_NOT_FOUND
  "message": "string",     // human-readable
  "requestId": "string" }  // correlation id for tracing

Global status codes apply across all endpoints:

  • 400 — malformed body / invalid field (e.g. weight out of range, unknown platform).
  • 401 — missing/invalid credentials · 403 — authenticated but not permitted (e.g. non-admin hitting a control-plane route, technician acting for another techId).
  • 404 — division / dispatch / technician not found.
  • 409 — duplicate reply on /dispatches/{id}/respond (the SETNX dedupe already rejected it); the first reply stands.
  • 500 — unexpected server error (correlate via requestId).

Two response types — two separate endpoints

The technician's two replies live at different paths because they have different scope:

  • Availability — POST /technicians/{id}/availability. Tech-scoped, no dispatchId. A general "I'm free at …" answer to the availability poll during the ~1 min ranking window; updates the technician's availability record that ranking reads.
  • Decision — POST /dispatches/{id}/respond. Dispatch-scoped. Accept/reject one specific offer; drives the offer loop, and a reject (or timeout) moves to the next ranked technician. This is the reply the worker is blocked on (BLPOP).

10. SNS Round-Trip

SNS is push-out only (fire-and-forget). The reply comes back through EC2 → Redis, where the worker is already blocked on BLPOP — so it wakes the instant the technician taps Accept.

Worker (Fargate) SNS Phone (Flutter) EC2 API Redis | Publish(endpointArn, {dispatchId,techId,job}) | | |------------------>|-------------->| | | | | push (APNs/FCM) | | | | tap Accept/Reject| | | |----------------->| POST /dispatches/{id}/respond | | | SETNX resp:done (dedupe) | | | LPUSH resp:{id}:{tech} | | |-------------->| | BLPOP wakes instantly <-------------------------------------------| | rank & assign (RDS) -> release lock -> XACK | |
Timeout rule: the worker's BLPOP timeout T must stay below the division lock TTL. On timeout the worker escalates to the next technician batch; the lock is never lost mid-flight.

11. Onboarding Plan

Everything that must be in place to take Auto-Dispatch from an empty production account to a live, division-by-division rollout. Four ordered phases — infra must exist before data seeding, data before client rollout, and everything before the first toggle flip.

Phase 0 — Infrastructure provisioning (one-time)

  • ElastiCache Redis cluster up, and create the consumer group (XGROUP CREATE dispatch:stream …) — workers cannot read the stream until it exists.
  • ECS Fargate ready: worker image pushed to ECR, task definition (1 vCPU / 2 GB), scale 0↔N policy.
  • SNS platform applications created — one APNs (upload Apple .p8 key), one FCM (Google key). Hard precondition for /devices/register: no push endpoint can exist until these are live.
  • IAM roles: SNS Publish, ECS scale control (boto3), ElastiCache access.

Phase 1 — Data seeding to DB (per division)

  • Default ranking config — seed each division's weights (distance, familiarity, priority, availability window) directly into the DB at production cutover.
  • Toggle default OFF — every division starts disabled. Safe default: nothing auto-dispatches until an admin explicitly opts in.
  • Escalation target — the human dispatcher/queue the "no technician accepted" path hands off to. Without it, escalation has nowhere to go.
  • Technician data readiness — each tech needs division, location source, and skills populated; ranking silently breaks on missing data.

Phase 2 — Client rollout & SNS push onboarding

Push is new to the platform, but signed-up technicians already exist on iOS/Android with no push token yet. SNS can only ring a technician once an endpointArn exists — an endpointArn is the per-device address SNS returns when you register a push token; you publish to that arn, not to the raw token. Onboarding must create it for both cohorts with no one-off migration job.

+

New technician

Signs up on a push-enabled build → grants permission → POST /devices/register fires at once. Arn exists before first dispatch. No gap.

↻

Existing technician

Account exists but no token, no arn — unreachable until they update the app, open it, and grant permission. The one cohort with a temporary gap.

  • Ship the push-enabled app + min-version gate — before enabling any division, or no one is reachable.
  • Token management — the app registers its token on first login, whenever the OS rotates it (reinstall/restore), and on a periodic (e.g. daily) refresh. Tokens stay valid for months, so this is a few calls per technician, not one per launch.
  • Backend upsert on (techId, token) — first call creates the endpoint, unchanged token no-ops, rotated token updates the arn.
  • Fallback if unreachable — a tech with no arn (or one SNS reports dead) is skipped to manual/escalation; the dispatch never hard-fails, and the tech re-registers on its next refresh.
Device token / endpointArn = PII. The push token and its SNS endpointArn are the one new piece of personal data this project stores (techId → endpointArn). They are treated as sensitive: encrypted at rest, access-limited to the dispatch backend, and kept only while the device is active — a rotated token overwrites the old arn (upsert) and a dead arn is cleaned up, so stale tokens do not accumulate. Technician location is not newly stored here — distance/ETA comes from the platform's existing location system, which auto-dispatch only reads, so its retention is unchanged and out of scope for this project.

Phase 3 — Go-live sequencing

  • Monitoring/alerting live first — push-adoption %, stream lag, lock-hold time, BLPOP-timeout rate.
  • Pilot one division — flip a single division ON, validate exactly-once assignment and the escalation path end-to-end.
  • Expand division-by-division — enable the rest once the pilot is clean; drop the manual fallback as endpoint adoption nears 100%.

Environments & deployment

  • Staging before prod — the change is validated in a staging environment first, then promoted to production. Staging and production each get their own isolated instances (separate ElastiCache Redis, separate RDS, separate Fargate service) — no shared state across environments, so a staging run can never touch live technician data.
  • CI/CD — client's existing pipeline. Auto-Dispatch is a one-time change to an existing platform, not a new service, so it introduces no new pipeline. Build, test, deploy, and rollback of the worker image and the Server A/B changes all follow the client's established deployment strategy; rollback is whatever that pipeline already provides (e.g. redeploy the previous image/task-definition).

12. Fault Tolerance

A dispatch request is handed to one worker to process. The system tracks that the request is "handed out but not yet finished." When the worker finishes, it marks the request done and the request clears. The goal: never lose a request if a worker dies, and never process the same request twice.

How a crashed or slow worker is handled

  1. Problem — worker crashes partway. The request is still marked "handed out, not finished," but nobody is actually working on it. It is stuck, and the customer waits forever.
  2. Rescue. If a request stays "not finished" for too long, another worker is allowed to take it over and process it. The stuck request is recovered.
  3. New danger. What if the first worker did not crash — just ran slow? Then the second worker takes over and processes the same request while the first is still working it — the same job offered to two technicians.
  4. Safeguard. Before offering a job, a worker must hold a claim on that technician, and only one worker can hold it at a time. If the first worker is just slow it still holds the claim, so the second worker is blocked — no double offer. If the first worker truly crashed, its claim releases automatically after a short time, so the second worker safely takes over.

The claim decides it: still held means "someone is alive and working — stay out"; released means "they are gone — go ahead."

Net effect — exactly-once: every request is processed even if a worker dies, and no request is ever processed twice even if a worker is slow. Nothing lost, nothing duplicated.

14. Future Improvements

🔄
Beyond new requests
Today auto-dispatch only picks up newly created requests. Extend it to act on other dispatch statuses too — e.g. re-dispatch on reject/timeout, reassign in-progress jobs, or reopen cancelled ones
🎖
Reward / feedback loop
Feed accept/reject and job-outcome history back into ranking — reward technicians who reliably accept and complete, so the shortlist self-tunes over time instead of using static weights
