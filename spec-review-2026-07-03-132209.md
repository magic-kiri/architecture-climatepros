## Executive summary

**Overall score: 5.9/10 — Significant gaps — revise before build**

This is a spec for a toggle-driven, division-isolated auto-dispatch pipeline layered onto ClimatePros' existing EC2/RDS platform via a new Redis + Fargate processing tier and an SNS notify/reply loop. It is unusually strong in places most specs skip — the cost projection is grounded in real unit-cost math, the crash/slow-worker fault-tolerance walkthrough is genuinely clear, and the operational flows model retries, timeouts, and escalation rather than only the happy path. But it is not yet build-ready: a crash-window race in the exactly-once completion path (FND-004) can double-process a dispatch, the primary architecture diagram contradicts the documented locking model on a stated invariant (FND-002), and none of the project's new persistent data (RDS status fields, availability record, endpointArn table) has a field-level schema (FND-007). Close those three first; the rest of the document is a solid foundation to build on.

**Verdict reason:** A Blocker (FND-004: an unaddressed crash-window race between the RDS assignment write and the stream XACK that can re-run the assignment flow on an already-assigned dispatch, undermining the document's own repeatedly-stated 'exactly-once' invariant) caps this regardless of average, and the 5.9/10 average independently lands in the same band — driven mainly by an undocumented persistent data schema (DAT, 3/10) and a self-acknowledged architecture-diagram/prose contradiction on the core locking model (ARC, 6/10).

**Gating findings** (the ones that must close before/early in build):
- `FND-004` (Blocker) — §4 step 6 states the completion order as "the worker writes to RDS, releases the lock, and XACKs the message" — leaving a crash window between the RDS write and the XACK. If the worker dies in that window, the message stays unacknowledged in the stream's PEL; once the (TTL-based) lock naturally expires, §4 step 4 / §12 say a surviving worker "runs the assignment flow" again from the top for any reclaimed message, with no stated check for whether the dispatch was already assigned. That can re-run ranking and re-offer (and re-assign) a dispatch that RDS already recorded as assigned to a different technician — directly contradicting the "exactly-once" invariant the document asserts as an achieved guarantee no fewer than four times (§1, §2, §6 callout, §12 "Net effect"). → Before a reclaimed/XCLAIMed message re-enters the assignment flow, have the worker check for an existing assignment (RDS lookup or a Redis "assigned:{dispatchId}" marker) and, if found, XACK and exit without re-offering. Alternatively make the RDS write and the lock-release/XACK sequence atomic (only release the lock after a successful XACK). Document whichever mechanism is chosen in §12 next to the existing crash/slow-worker walkthrough.
- `FND-007` (Major) — The document repeatedly references new persisted data — "dispatch status fields" added to RDS (§2 non-goals), a technician's general availability record (§9 POST /technicians/{id}/availability), and the techId→endpointArn mapping (§11) — but none of it has a field-level schema: no table/column names, types, nullability, keys, or indexes, and no migration/versioning approach for the RDS changes. The Redis *ephemeral* coordination structures are documented well (§6's table); the *persistent* system-of-record changes are not. → Add a short schema section (or ERD) enumerating: the new/changed RDS columns (e.g. Dispatch.status enum + allowed values, Dispatch.assignedTechId, Dispatch.assignedAt), the endpointArn storage table (columns, a unique key on techId+platform for the upsert path described in §11, and its lookup index), and how/where the availability record is modeled and read by the ranking step.
- `FND-002` (Major) — The architecture diagram (frag-architecture.html, embedded in §4) still draws and labels a per-division lock (lock:div:Div_A / lock:div:*) as the concurrency mechanism, directly contradicting the actual, documented model — a per-technician lock (lock:tech:{techId}) in §6 Redis Data Structures — which is what makes the stated goal "two requests run in parallel when their candidate technicians are disjoint (even within the same division)" (§2) true. The document even flags the mismatch itself ("diagram redraw pending") but ships it uncorrected, so a team building from the diagram alone would implement per-division serialization and silently defeat one of the four stated invariants. → Redraw frag-architecture.html's Fargate-pool task cards and Redis-layer panel to show per-candidate-technician locking (lock:tech:{techId}) consistent with §6/§8/§12, before it is used as the build reference.
- `FND-016` (Major) — There is no test strategy anywhere in the document for the new distributed-locking / exactly-once logic — the single riskiest piece of new code in this project (see FND-004). No unit tests for the lock/claim logic, no integration test simulating a worker crash or a slow-worker/stall, and no load or chaos testing are mentioned before the §11 Phase 3 pilot. → Add a testing subsection: at minimum, a chaos/failure-injection test that kills a worker mid-assignment and asserts no duplicate SNS offer or duplicate RDS write occurs, run and passing before the single-division pilot begins.
- `FND-014` (Major) — No secrets-management approach is stated anywhere — notably for the Apple .p8 APNs signing key (§11 Phase 0: "upload Apple .p8 key") and any AWS credentials the workers/Server B use to call ECS/SNS/ElastiCache. → State where these secrets live (e.g. AWS Secrets Manager or Parameter Store with rotation) and confirm none are baked into the worker container image or task-definition environment variables as plaintext.

**Notable strengths:**
- The ElastiCache single-node SPOF is named, explained as a deliberate cost trade-off, and paired with a concrete fallback (manual dispatch) — exactly how an accepted architectural risk should be documented.
- The Cost Projection section derives every number from stated volume assumptions and real AWS unit pricing, with three scenarios and a quantified scale-to-zero payoff — the strongest section in the document.
- The retry-until-shortlist-exhausted-then-escalate flow, and the plain-language crash/slow-worker walkthrough in §12, model unhappy paths clearly rather than only the happy path.

## Area detail

### 1. Overview & Problem Framing — 8/10
**Assessment.** The problem (admin-bottlenecked manual dispatch) is stated crisply, and §2's four goals/invariants (exactly-once, conflict-aware concurrency, no-polling reply, scale-to-zero) read as genuine engineering invariants rather than marketing adjectives. The success metric — escalation-to-human rate ≤ Y%, with Y explicitly deferred to the pilot baseline — is a thoughtful, honestly-scoped measurable criterion rather than a vague "fast/scalable." Non-goals are explicit and useful (manual flow untouched, no UI change beyond the toggle, no RDS schema change beyond dispatch-status fields).
**Findings.** FND-001
**Suggestions.** Pull the volume assumption that currently only appears inside the Cost Projection example into §2 as a stated business assumption, and reuse it consistently.
**Strengths.** Deferring the numeric escalation-rate target to the pilot baseline (rather than guessing a number) is exactly the kind of surfaced uncertainty a strong spec should have.

### 2. Architecture & System Design — 6/10
**Assessment.** There's a real interactive architecture diagram, clearly-scoped components (Dashboard, Server A/B, Fargate pool, Redis, RDS, SNS), an explicit request-flow narrative, and honest failure-mode reasoning (the ElastiCache single-node risk is called out and paired with a concrete fallback rather than hidden). The scoring is held down by one significant, self-acknowledged defect: the primary diagram contradicts the documented locking model on a core invariant (FND-002), which is exactly the kind of diagram/prose mismatch the rubric treats as a red flag. There's also no consolidated NFR/SLO statement (FND-003).
**Findings.** FND-002, FND-003
**Suggestions.** Redraw frag-architecture.html to match the per-technician lock model before using it to build from, and add a short NFR/SLO table consolidating the timing constants that are currently scattered across the flows sections.
**Strengths.** The ElastiCache HA callout (§5) is a model of how to document an accepted architectural risk: it names the SPOF, the trade-off reason, and a concrete, credible fallback (manual dispatch) instead of hand-waving it.

### 3. Feature Flows & System Sequencing — 4/10
**Assessment.** This section has real strengths — the three control flows (enable/disable/new-dispatch), the per-request assignment loop with an explicit retry-until-exhausted-then-escalate path, the SNS round-trip sequence, and the Socratic crash/slow-worker walkthrough in §12 are all clearly sequenced with unhappy paths modeled, which is more than most specs attempt. The score is capped by a Blocker: the worker's write-RDS-then-XACK ordering (§4 step 6) leaves a crash window that can lead to re-running the assignment flow on an already-assigned dispatch, violating the "exactly-once" guarantee the document asserts as achieved (FND-004). Several timing constants that other sections depend on for correctness are also never given concrete values (FND-005), and SNS Publish-failure handling is unaddressed (FND-006).
**Findings.** FND-004, FND-005, FND-006
**Suggestions.** Close FND-004 first — add an explicit already-assigned check (or an atomic write+ack) to the reclaim path in §12 — since this is the one gap that undermines the document's central correctness claim. Then fill in the concrete timeout/TTL values and the SNS-failure handling.
**Strengths.** The retry-until-exhausted-then-escalate loop and the plain-language crash/slow-worker walkthrough in §12 are genuinely strong, readable unhappy-path documentation.

### 4. Data Schema & Modeling — 3/10
**Assessment.** The ephemeral Redis coordination structures are documented well (§6's table: stream, per-tech lock, reply list, each with key pattern and purpose). But every piece of *persistent* new data this project introduces — the RDS dispatch-status fields, the technician availability record, and the techId→endpointArn mapping — is referenced only in prose, with no field names, types, constraints, keys/indexes, or migration approach given anywhere (FND-007). PII handling is a partial strength (the endpointArn is explicitly classified and its lifecycle described) but doesn't extend to the location/address data the ranking algorithm consumes (FND-008).
**Findings.** FND-007, FND-008
**Suggestions.** Add a schema section or ERD for the three new/changed persistent structures (dispatch-status fields, availability record, endpointArn table) with field types, keys, and a migration note — this is the single largest gap in an otherwise build-ready-leaning document.
**Strengths.** The endpointArn PII callout in §11 (encrypted at rest, access-limited, upsert-cleans-stale-tokens) is a genuinely good model for how the missing RDS fields should be documented too.

### 5. API Contracts — 6/10
**Assessment.** The five new endpoints are enumerated with method, path, caller, purpose, and request body; auth is cleanly split control-plane vs data-plane against existing middleware; and the error contract (stable code/message/requestId envelope, enumerated global status codes, and a specifically-reasoned 409 for the SETNX-deduped reply) is unusually complete for a spec at this stage. The gap that holds the score down is that no endpoint shows a success-response schema (FND-009) — most consequential for the config GET, whose whole purpose depends on a shape that's never shown. Versioning and rate limiting are also unaddressed (FND-010, FND-011).
**Findings.** FND-009, FND-010, FND-011
**Suggestions.** Add success-response examples for all five endpoints (the GET config response most urgently), then state versioning and rate-limiting positions even if the answer is "unchanged from the existing platform."
**Strengths.** The "two response types, two endpoints" design rationale (§9) and the enumerated, endpoint-specific error contract are genuinely strong, client-ready API design thinking.

### 6. Libraries, Frameworks & Tech Stack — 7/10
**Assessment.** §3 names concrete, well-justified technologies for every layer (Flutter, SNS, APNs+FCM, FastAPI, redis.asyncio, ElastiCache, ECS Fargate, boto3) with a clear role for each, and the "why SNS + FCM both" callout is a good example of justifying a non-obvious choice. The stack is entirely mainstream/low-risk (AWS-native managed services plus long-established Python libraries), which limits the practical impact of the gaps below.
**Findings.** FND-012, FND-013
**Suggestions.** Pin at least the worker's direct Python dependencies to a version, and add a one-line licensing confirmation.
**Strengths.** Every component in the stack table is named with a specific, non-generic role rather than described only by category (e.g. "a queue").

### 7. Observability & Traceability — N/A
**Assessment.** N/A — the system has no LLM/generative-AI component. The ranking algorithm (§8) is a deterministic weighted formula over stated inputs (ETA, familiarity), not a model making judgment calls, so AI-specific observability (prompts/completions/tokens/cost tracing) doesn't apply. Ordinary operational observability is covered instead under Onboarding/Go-live (§11 Phase 3: push-adoption %, stream lag, lock-hold time, BLPOP-timeout rate), which is the right substitute for this system.
**Findings.** None; covered well (or N/A — see assessment).

### 8. Evaluation Strategy — N/A
**Assessment.** N/A — no model output requires an eval/golden-set strategy; the ranking formula's correctness is a matter of algorithm testing (see FND-016 for the closest analogue: no stated test plan for the locking logic), not model evaluation.
**Findings.** None; covered well (or N/A — see assessment).

### 9. Feedback Loops & Continuous Improvement — N/A
**Assessment.** N/A for this phase — there's no learned model to retrain or drift-monitor today. Notably, §14 Future Improvements explicitly proposes a future "reward/feedback loop" that would feed accept/reject and job-outcome history back into ranking so weights self-tune — which confirms today's ranking is intentionally static/rules-based, not a system this area applies to yet.
**Findings.** None; covered well (or N/A — see assessment).

### 10. AI Compliance, Safety & Governance — N/A
**Assessment.** N/A — no model provider, prompt, or generated content is in scope, so AI-specific governance (data-use terms, prompt-injection defense, hallucination mitigation) doesn't apply. General data-privacy handling for the one new PII field (device token/endpointArn) is assessed instead under Data Schema & Modeling (FND-008).
**Findings.** None; covered well (or N/A — see assessment).

### 11. Infrastructure & Environment Setup — 5/10
**Assessment.** Environment separation is handled well — staging and production get fully isolated instances of every new resource (§11), which is exactly the right posture. IAM roles are named at a high level (SNS Publish, ECS scale control, ElastiCache access). What's missing is anything on secrets management for the sensitive APNs signing key and AWS credentials (FND-014), and any IaC tool or networking/VPC/security-group story for the new resources (FND-015) — Phase 0 currently reads as a manual provisioning checklist.
**Findings.** FND-014, FND-015
**Suggestions.** State the secrets-management mechanism for the APNs key and any new credentials, name the IaC tool used for Phase 0 provisioning, and add a short networking paragraph (VPC/security groups) for the new ElastiCache and Fargate resources.
**Strengths.** Staging/production isolation (separate ElastiCache, RDS, Fargate service per environment, §11) is explicitly called out and is exactly the right practice.

### 12. CI/CD & Release Management — 5/10
**Assessment.** Reusing the client's existing CI/CD pipeline rather than inventing a new one is a legitimate, explicitly-stated scope decision for an augmentation to an existing platform (§11), and the division-by-division go-live sequencing (§11 Phase 3: monitoring first, pilot one division, then expand) functions as a sensible business-level canary rollout. What's missing is any test strategy for the new distributed-locking logic before it reaches production (FND-016) — the single riskiest piece of new code in the project — and any augmentation of the inherited rollback plan for this project's new failure modes, like stuck Redis locks (FND-017).
**Findings.** FND-016, FND-017
**Suggestions.** Add a chaos/failure-injection test plan for the locking logic that must pass before the single-division pilot, and a short runbook addendum for clearing Redis state if a bad worker deploy needs rolling back mid-flight.
**Strengths.** The Phase 3 go-live sequencing (monitoring live first, then a single pilot division, then division-by-division expansion) is a sound, low-risk progressive-rollout strategy even without a formal blue/green deploy mechanism.

### 13. Cost Projection — 9/10
**Assessment.** This is the strongest section in the document. The Fargate cost is derived from actual vCPU/GB-hour pricing rather than guessed; ElastiCache's fixed cost is computed; SNS push cost is computed from a stated volume assumption (500 dispatches/day × 5 techs × 30) and correctly shown to land inside the free tier; three real scenarios (Light/2h, 8h-ON, 24×7) are tabulated with a per-scenario total; sunk EC2/RDS cost is correctly excluded from the delta; and the scale-to-zero payoff is quantified (~12×). The one gap is a scaling-clarity nuance, not a missing assumption (FND-018).
**Findings.** FND-018
**Suggestions.** Add one sentence clarifying whether the Fargate pool (and its N) is shared across all enabled divisions or provisioned per division, so the cost table reads correctly once more than one division is live.
**Strengths.** Grounded token/unit-cost math with stated volume assumptions and three real scenarios (not a single hand-waved number) is exactly what a strong cost-projection section looks like — this should be the template for the rest of the client's specs.
