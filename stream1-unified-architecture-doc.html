1. Stream 1 Overview

ClimatePros runs commercial refrigeration & HVAC field service: ~900–1,000 technicians , 46 branches , 10,000+ sites . Work orders arrive automatically. Everything after that still runs on a phone call and a technician's memory . Three use cases, three bottlenecks, one job. Where AI sits: Use Case A is a deterministic algorithm — no LLM . It replaces a decision a dispatcher already makes by hand, so it must be explainable and repeatable. Use Cases B and C use AI, and in both the technician can always override it . ~900–1,000 Technicians 46 Branches 10,000+ Sites A Algorithm · no LLM

Auto-Dispatch — finding the right technician

Web portal · Dispatcher A dispatcher has a job ready and ~40 candidate techs in the region. The four things that decide the right one — how far, how familiar with the site, how soon free, how urgent — are each buried behind separate clicks or held in the dispatcher's head . Confirming one means dialling candidates one at a time , ~2–3 min each; no answer → call the next. Why it hurts: two dispatchers per branch are the throughput ceiling — more job volume means more headcount, not faster dispatch. We solve: rank on those same four factors; push an accept/decline offer that cascades automatically. No LLM — every assignment explainable. B AI · tech overrides

Job Summarisation Copilot — changing the job status

Mobile · Technician at end of job Every job ends with a mandatory status change , and behind it sits a wall of forms plus two free-text notes — one for the customer, one for the office. Done properly it takes 10–15 min , often in a machine room with no signal where voice dictation is only ~30% accurate . Why it hurts: so the tech skimps — ~40% of 16.3M notes are ≤40 chars , the most common note is literally "checked history". Downstream the office can't bill or route ("Replaced motor" — but no motor in the parts list). We solve: restructure rough words into a clean customer/office note and suggest form values from similar jobs; flag what's missing. Never fabricates, never blocks Save. Target: 10–15 min → ~15 s . C AI · tech overrides

Technician Parts Finder — finding the part that isn't on the truck

Mobile · Technician on-site On site the tech needs a part. Three sources the app already answers — truck, nearby techs, warehouse. The fourth, a third-party supplier , is a phone call: Google search, 1–3 calls, hope they answer . Why it hurts: the same physical part carries a different number at every vendor , and the supplier API matches exact part number only — no fuzzy logic . A human bridges that gap by phone under emergency pressure; miss it and it's a return dispatch — a second truck roll, job can't finish today. We solve: AI suggests the likely part; one search shows where it is across all four sources with location and distance. No price ranking, no ordering. Work order in → (A) the right tech is offered the job on the web portal → tech arrives on site → (C) the missing part is found on mobile without a phone call → (B) the closeout note writes itself. Full step-by-step diagrams for all three: see §5 Operational Flows .

What follows is the overall flow: which entity talks to which, and why. Per-use-case wiring (queues, locks, schemas, ranking, scoring) is detailed in §2b — this section stays deliberately high-level.

Entry · single front door

Web App + Mobile App → AWS EC2 (.NET APIs) Both clients speak only to the existing .NET APIs on the EC2 application host over HTTPS. Neither the new infrastructure nor the models are ever reached directly — the legacy platform stays the single entry point and gains just two new additions: an AI proxy route and an ECS task-scale controller (spins workers up/down).

Data · two stores, cleanly split

EC2 ↔ SQL Server (AWS) ↔ ECS workers | FastAPI ↔ MongoDB (Azure) SQL Server stays the system of record for business data — the EC2 .NET APIs and the new ECS dispatch workers read/write it directly, all inside AWS. The FastAPI AI server never connects to SQL Server : it owns a separate MongoDB (Azure Cosmos DB for MongoDB) for summaries, part-search results, llm_calls traces and eval data. Any business context it needs arrives in the request payload from the .NET AI proxy.

Dispatch · Use Case A · no LLM

.NET → ElastiCache → ECS Fargate → SNS → Mobile When auto-dispatch is on, the .NET API publishes the job to ElastiCache for Redis and the scale monitor spins ECS Fargate workers 0→1 . Workers consume the stream, rank technicians, and push accept/decline offers out through Amazon SNS (APNs/FCM) to the technician's phone. Entirely on AWS — no cross-cloud hop. The reply path returns via the .NET API. Deterministic — no model involved.

AI · Use Cases B & C

.NET (AWS) → FastAPI AI Server (Azure) → Vector DB / MongoDB For summarisation (B) and parts finding (C), the .NET AI proxy forwards the request — with the job context in the payload — across to the FastAPI AI Server on Azure , the single central AI service and the only path to the models . It queries/upserts the Vector DB for historical retrieval and persists its outputs to its own MongoDB . This AWS→Azure call is the sole cross-cloud dependency ; the AI stack is self-contained behind it.

Models · private, on-prem

FastAPI → LiteLLM Gateway → self-hosted LLM / embedding / Gemini All inference goes through the on-prem LiteLLM Gateway , which routes to the self-hosted qwen3-vl-moe (vLLM) and bge-m3 embedding, with Gemini as external fallback . No service calls a model directly — LiteLLM is the sole gate, keeping data inside ClimatePros infra.

Observability · cross-cutting

all services → OpenTelemetry / CloudWatch + Azure Monitor Every service emits traces and logs to a shared observability layer (OpenTelemetry) — CloudWatch on the AWS side, Azure Monitor for the AI stack.

Compute sizing

New compute tiers — AWS ECS Fargate for dispatch workers, Azure Container Apps for the AI server — run small and scale horizontally, not vertically. Baseline instance size is 0.5 vCPU / 1 GB RAM across both, which handles 60+ concurrent dispatch operations per instance comfortably; load is met by adding replicas/tasks, not bigger boxes.

Network topology

The existing platform and all new non-AI infrastructure sit inside a single AWS VPC , matching FieldJetX: EC2 (the .NET hosts) and ECS Fargate (dispatch workers) in an apps subnet, and ElastiCache for Redis and SQL Server reached over private subnets — neither exposes a public IP, so all worker↔broker and worker↔database traffic stays inside the VPC. The only public entry point is the .NET API, fronted by an AWS load balancer / API gateway where WAF filtering and TLS termination happen; the mobile app (B, C) and web console (A) reach the API there. A separate Azure VNet holds only the AI stack: Container Apps (the FastAPI AI server) in an apps subnet, with MongoDB and the vector store reached over private endpoints in a data subnet. The one cross-cloud path in Stream 1 is the .NET AI-proxy route on AWS calling the FastAPI AI server on Azure — technician phones never reach either side directly, and the AI server never reaches AWS SQL Server. From there, the AI server has two private egress paths of its own: the on-prem model stack (LiteLLM + self-hosted models) over a VPN / private link to the ClimatePros datacenter, and a fallback to Google Gemini over outbound HTTPS. That gives three trust boundaries to enforce: Internet→AWS (load balancer / WAF), AWS→Azure (the single AI-request hop — VPN/peering target state, public endpoint + IP allow-list as fallback), and Azure→on-prem (VPN / private link). Cross-cloud dependency: the seam isn't the database — AWS SQL Server is read and written only by AWS-side compute (EC2 and ECS Fargate), so Auto-Dispatch (A) never leaves AWS. The one cross-cloud hop is the AI request itself: when a technician triggers a summarisation (B) or parts search (C), the .NET AI-proxy route on AWS EC2 calls the FastAPI AI Server on Azure Container Apps, carrying the job context in its payload, and gets a response back. - Network path: target state is a site-to-site VPN or VPC-to-VNet private peering between the AWS account and the Azure subscription; until that's provisioned, the fallback is a public HTTPS endpoint on the AI server, locked down by IP allow-listing / mTLS. - Added latency: only the B/C request path pays inter-cloud round-trip time — once per summarisation or parts search, not per SQL call — and this has to be budgeted into the P95 targets in §9 Observability & Evals. - Cost: AWS bills egress on the .NET proxy's outbound call to Azure; this is one request/response pair per B/C call, not a per-row data-transfer cost, and belongs in §10 Cost Projection. - Single seam: this AI-request hop is the only place Stream 1 crosses clouds — SQL Server, the message broker, the dispatch workers, and push all stay inside AWS. If the link goes down, B and C fall back to their existing manual path (forms without AI assist, no parts search); Auto-Dispatch (A) is entirely unaffected since it never touches Azure.

Amazon SNS round-trip

The mechanics behind step 4's push — fire-and-forget out, a different path back in. Component-level diagram: §2 · Use Case A · step 3. 1

Worker publishes the offer

The winning ECS Fargate worker calls the Amazon SNS Publish API with the technician's platform endpoint ARN and the offer payload {dispatchId, techId, job} . 2

Push is delivered

Amazon SNS fans the message out to the platform application endpoint through APNs (iOS) or FCM (Android) straight to the technician's phone. 3

Technician responds

Tapping Accept/Reject in the FieldJetX app POSTs the reply to the AWS EC2 API, which de-dupes with SETNX resp:done and LPUSH es it onto a per-technician Redis reply list. 4

Worker wakes instantly

The same worker that sent the offer is already blocked on BLPOP for that key — no polling, no delay. 5

Rank & assign

On Accept the worker writes the assignment to SQL Server, releases the division lock, and XACK s the stream message — closing the loop.

A Auto-Dispatch — Ranking Algorithm

This is the detail behind step 3 ( “Rank the technicians” ) of the assignment loop in §5 . It turns each candidate's availability, distance, and visit history into a single ordered shortlist. One formula covers every case — its behavior is tuned by a single weight w chosen from the job's dispatch type.

Inputs

  • free i — minutes until technician i is available (time left on current job)
  • dist i — miles from technician i to the jobsite
  • visits i — prior visits by technician i to this customer (familiarity)
  • AVG_SPEED — average truck speed in mph, a configurable constant
  • dispatchType — Emergency · High Priority · Medium Priority ↓

Step A — unify availability + distance into one ETA

Distance can't be compared to wait-time directly. Convert distance to travel time using the average truck speed, then add the wait, so every technician collapses to one number : minutes-until-on-site. Lower is better.

travel_i = (dist_i / AVG_SPEED) * 60      # miles -> minutes
eta_i    = free_i + travel_i              # total minutes until tech is on site

↓

Step B — weighted score

Blend ETA and visit count into one score. Both must be on a 0–1 scale where higher is better, so min-max normalize each across this candidate set, then weight by w (the speed share). A pure ranking is just an endpoint: w=1 sorts by ETA only, w=0 by visits only — no separate sort needed.

speed_score_i = (eta_max - eta_i)      / (eta_max - eta_min)      # lowest eta  -> 1.0
fam_score_i   = (visits_i - visits_min)/ (visits_max - visits_min) # most visits -> 1.0

score_i = w * speed_score_i + (1 - w) * fam_score_i               # w = speed weight
# sort score_i descending -> rank 1 = offer target

Edge cases: a single candidate is rank 1 by default; if all ETAs tie the speed term is flat and familiarity breaks the tie (and vice-versa). ↓

Step C — pick w from the dispatch type

Emergency and Medium are just the two ends ( w=1 , w=0 ) of the same combined formula — so one code path serves all three .

Dispatch Type Strategy w (speed) Result
Emergency Speed-Based (locked) 1.0 Pure ETA; familiarity ignored — lowest combined time wins
High Priority Combined 0.2 (Speed 20 / Fam 80) Weighted blend; weight configurable per strategy
Medium Priority Familiarity-Based 0.0 Pure visit count — most familiar tech wins

One formula, three behaviors: the dispatch type only sets w . Emergency ( w=1 ) reduces to pure speed, Medium ( w=0 ) to pure familiarity, High blends them — no separate ranking code per type. The resulting ordered shortlist feeds directly into step 4 (offer to the top-ranked technician) in §5 . Future factor — skill gate: when technician skill data is available ( 1 ≤ skill i ≤ 5 ) and a job carries a minimum required skill, it enters as a hard gate, not a score term . Filter it in step 1 when building the candidate list — keep technician i only if skill i ≥ job.minSkill — so under-skilled technicians never reach ranking. The speed/familiarity scoring is untouched; only the candidate set shrinks.

How retrieval works

Everything the copilot retrieves is deterministic SQL over the client's real dispatch history : explainable, zero new infrastructure, and already measured against a full year of staging data (252,615 dispatches). This is what replaced the earlier vector-index plan after the 2026-07-07 architecture call.

Need Mechanism
Same-site history (briefing) Keyed SQL query: past visit digests for the same customer and site, most recent first.
Similar past issues (briefing) Deterministic lookup: 2–3 recent dispatches with the same equipment type and problem code are pulled and handed to the LLM as context. No embeddings, no similarity index.
Part suggestions SQL co-occurrence: a frequency table keyed on (equipment manufacturer type × problem code) → most-used parts, with fallback to equipment type alone, then global top parts. One SQL aggregation, fully explainable.
Compliance procedures Always fetched live from the source system, never cached or embedded: they are compliance-critical and change.

The measured baseline (backtested on staging, 2026-07-08)

The co-occurrence method was trained on 11 months of real dispatches and tested on the final month (4,151 dispatches with installed parts, 3,100 distinct parts in play). “Hit” means at least one actually-installed part appeared in the top-k suggestion list:

Label-quality reality (what the EDA must account for)

An audit of the last 12 months of staging data showed the structured outcome codes are far weaker than they look: root-cause and failure codes have been dead since 2021, the problem code's top value is OTHER at 38%, and the summary code is SERVICE for 88% of filled rows. The genuine predictive signal lives in the free-text complaint ( DispatchReason , 230k+ distinct values) and technician notes , plus equipment identity. Any classical-ML phase therefore must include text feature engineering; training on code columns alone will underperform the baseline above.

C Parts Finder — Matching & Sourcing Logic

Prediction is retrieval-augmented: find the most similar past dispatches, then rank the parts those dispatches used, weighting closeness over raw frequency so one near-identical job outranks several loosely-similar ones. Once parts are identified, the Source API works out where to get them from.

Pipeline

  • Asymmetric embedding. Historical reasons are embedded at index time with a document task type; the live dispatch reason is embedded per request with a query task type. Both run on the self-hosted embedding model on customer hardware — dispatch text never goes to an external AI provider.
  • Retrieve. Search the Azure-hosted vector store for the top K = 15 nearest neighbors, returning cosine distances and each neighbor's partsUsed .
  • Rank & aggregate. The self-hosted LLM ranks & aggregates the retrieved parts: convert distance to similarity, gate on a threshold, and accumulate a cubed-similarity score per part.
  • Confidence & select. Normalize scores, clamp to a confidence band, return the top parts, and pre-select the confident ones.

Observability is operational and unified: one tracing/logging layer, introduced fresh by this project ( §3 Technology Stack, §4 Infrastructure), watches all three use cases the same way. Evals are about AI output quality and only apply where a model is in the loop — Auto-Dispatch (A) is a deterministic ranking formula ( §6 Core Logic) with nothing to eval; Job Summarisation (B) already has a working, production-grounded eval loop, lifted at full fidelity below; Parts Finder (C) today only validates retrieval quality on a held-out set of recent dispatches and does not yet have B's correction-based feedback loop — closing that gap is future work, not part of this architecture.

Unified Observability — OpenTelemetry Tracing + CloudWatch / Azure Monitor Logs

Every service in Stream 1 — the AWS EC2 host running both .NET APIs, the AWS ECS Fargate dispatch-worker pool (A), the Azure Container Apps FastAPI AI server (B, C), the Redis-fed worker loop, and every vector-store call — emits OpenTelemetry traces and structured logs. AWS-side services report into CloudWatch; the Azure AI stack reports into an Azure Monitor workspace, and trace context is propagated across the single AWS→Azure hop so one dispatch is one trace ( §3 , §4 ). This was an abstract, “not yet designed” placeholder in the source design; here it is the one piece of infrastructure every use case shares, so it is specified once instead of three times.

📡 Distributed traces

One trace per request, spanning every hop it takes — .NET proxy → Container Apps → AI server → LiteLLM → model, or .NET → Redis Stream → worker → SQL Server. The cross-cloud hop to AWS SQL Server ( §4 ) is a span like any other, so the added round-trip is visible, not hidden.

📋 Structured logs

Every service logs to Azure Monitor in one schema. Each entry carries the same requestId issued in the error envelope ( §8 API Reference), so a failed call traces from the client-visible error code back through every hop it touched.

🔄 Correlation

requestId is the join key across traces, logs, and the AI-specific tables in §7 Data & Schema ( the llm_calls collection , the summary_edits collection ) — so a slow trace, a log line, and an eval finding for the same request all resolve to one id. P95 targets — open item: §4 Infrastructure flags that cross-cloud AWS SQL Server round-trips must be budgeted into per-flow P95 targets, especially the Auto-Dispatch worker's per-request SQL calls. No formal SLOs exist yet in any of the three source designs; the inputs this document already establishes are the ~1 min technician-availability window and BLPOP reply-wait timeout (A, §5 Operational Flows), the ~6–7s LLM-bound /summarise / /analyse calls (B, §8 ), and the <200ms / <50ms deterministic endpoints (B/C, §8 ). Setting numeric P95 targets per flow, inclusive of the cross-cloud SQL leg, is follow-up work once Azure Monitor is live and has real traffic to baseline against — not something any source design specified.

B Evals — the Feedback Loop

Every AI interaction is persisted in the client's own database, so quality is measured from production reality, not vibes. 📈

The feedback loop

Log everything → corrections become ground truth → changes must beat the eval set. - the llm_calls collection records provider, model, tokens, latency, and outcome for every call: cost and reliability are queryable at any time. - the summary_edits collection records every human correction to an AI section: this is labelled ground truth generated by normal usage. - Eval set is built from those corrected rows and re-run before any prompt, ticket-standard, or provider/model change ships. - Headline metric: edit-rate per section : which of the 12 sections the AI gets right, tracked over time and per customer. Traceability: because prompts are built from a versioned ticket_standard.md and every call is logged with its model id, any ticket in production can be traced back to exactly which standard version and model produced it. How we view it: a lightweight dashboard page ( GET /admin/dashboard , §8 API Reference) is served by the same FastAPI container and reads straight from the AI MongoDB collections: no separate web app, no new hosting. Access is proxied through the .NET backend with an admin-role check on the existing Entra token, the same pattern as every other AI route, so the service stays fully private and no new login surface is created. Eval runs themselves are offline jobs over the summary_edits collection , not a hosted service. The eval set inherits weak labels, not clean ones: the same audit that shaped the retrieval baseline ( §6 Core Logic · B · Label-quality reality) found the structured outcome codes are mostly dead signal — root-cause/failure codes unused since 2021, problem code OTHER at 38%, summary code SERVICE for 88% of filled rows. The real predictive signal is free text ( DispatchReason , technician notes). the summary_edits collection works around this because it labels the model's actual output, not the weak structured codes — but it also means the eval set is only as good as what technicians bother to correct, not an independently audited ground truth.

Fault Tolerance

How a crashed or slow worker is handled

A dispatch request is handed to one worker to process. The system tracks that the request is "handed out but not yet finished" ( §7 Data & Schema · Amazon ElastiCache for Redis structures). When the worker finishes, it marks the request done and the request clears. The goal: never lose a request if a worker dies, and never process the same request twice. - Problem — worker crashes partway. The request is still marked "handed out, not finished," but nobody is actually working on it. It is stuck, and the customer waits forever. - Rescue. If a request stays "not finished" for too long, another worker is allowed to take it over and process it. The stuck request is recovered. - New danger. What if the first worker did not crash — just ran slow? Then the second worker takes over and processes the same request while the first is still working it — the same job offered to two technicians. - Safeguard. Before offering a job, a worker must hold a claim on that technician, and only one worker can hold it at a time. If the first worker is just slow it still holds the claim , so the second worker is blocked — no double offer. If the first worker truly crashed, its claim releases automatically after a short time, so the second worker safely takes over. The claim decides it: still held means "someone is alive and working — stay out"; released means "they are gone — go ahead." Net effect — exactly-once: every request is processed even if a worker dies, and no request is ever processed twice even if a worker is slow. Nothing lost, nothing duplicated.

Non-goals

A Auto-Dispatch

  • Not route optimization — closest-available-responder, like a 911 dispatch. It ranks who answers next, not the most efficient multi-stop route.
  • Deterministic, no LLM — a weighted-sum over stated inputs with configured (not learned) weights, so every assignment is explainable and repeatable.
  • The existing manual dispatch flow is untouched — a division with the toggle OFF behaves exactly as today.
  • No UI change beyond the toggle and its configuration (task count N ).
  • No change to the SQL Server system-of-record schema beyond dispatch status fields.

B Job Summarisation

  • Never fabricates. The ticket is generated from what is actually available — a missing block degrades to a MISSING placeholder, never an invented one ( §6 Core Logic, §8 API Reference).
  • Never blocks Save. Every failure mode — malformed output, gateway outage, saturation — degrades to the manual recap; submission is never gated on the AI tier ( §11 Fault Tolerance).
  • Completeness over prose. The headline isn't prettier writing — that's table stakes — it's cross-checking the note against parts, time and photos actually logged and surfacing what's missing.

C Parts Finder

  • No price ranking, no ordering. The tech decides where to pick a part up — the system shows the part, the place and the distance, and stops there.
  • One supplier for the POC (United, via the existing CP API Gateway); more suppliers is future work, not this scope.
  • Not replacing technician judgment — predictions are suggestions the tech can add, swap or ignore, never auto-committed.
  • No automatic purchasing or PO creation from the vendor, and no warehouse/inventory management — stock levels stay owned by the system of record.
