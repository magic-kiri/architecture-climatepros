Job Summarisation Copilot

System Design · Use Case B

An AI copilot inside the technician's mobile app: it briefs the technician on the site's history before arrival, drafts the job write-up, and blocks incomplete tickets before submission. It runs as a private, containerized FastAPI tier alongside the existing FieldJetX platform, using the client's own LLM gateway (qwen3-vl + nomic-embed) and deterministic SQL retrieval over real dispatch history.

1. What is Use Case B?

Every service visit ends with paperwork: the technician has to describe what was wrong, what they did, what parts they used, and whether the customer's compliance rules were followed. Today that write-up is typed by hand, its quality depends entirely on who is typing, and mistakes are only discovered days later in the office, when the fix is a phone call or a repeat truck roll. Use Case B puts an AI copilot inside the technician's mobile app that does three things: it briefs the technician on the site's history before they arrive, it drafts the job write-up from what they entered in the app, and it checks the ticket for missing or vague information before it can be submitted, so problems are caught on site, not days later.

2. Problem & Goals

Today the job record is whatever the technician types by hand at the end of a visit. Quality depends entirely on who is typing, technicians arrive without the benefit of the site's service history, and gaps (missing refrigerant data, photos, unmet compliance steps) are found by the office days later, when the fix is a phone call or a repeat truck roll.

⚠

Goals & invariants

What the copilot must guarantee.

  • Complete before leaving: critical gaps are surfaced and fixed on site; the ticket that reaches the office is clean.
  • Unchanged technician journey: same wizard, same submit; the AI prepares, drafts, and checks alongside it.
  • Single auth system: the app keeps its existing token; AI calls are proxied server-to-server by the .NET backend. The AI server has no public URL.
  • Existing platform untouched: the project adds one proxy route, one AI service tier, and one isolated ai.* schema; no business table or existing endpoint changes. The ai.* schema is created with client DBA approval.
  • Data stays private: all AI runs on the client's own models: qwen3-vl for generation and nomic-embed for embeddings, both served by their self-hosted private gateway. Prompts and job data never leave client-controlled infrastructure, and there is no third-party model dependency.
  • No accuracy commitments: quality numbers are targets, not contractual promises. A measured baseline (Section 12) comes first, and wider rollout is gated on roughly a 10% pilot.

Private by design: the FastAPI service has no public URL and does not validate end-user tokens itself. The .NET proxy validates the existing OAuth2/Entra token, strips user credentials, adds an internal API key, and forwards server-to-server. The proxy's HTTP timeout is extended (20–30s) to tolerate LLM latency; the load-balancer idle timeout is set ≥ 120s for the same reason.
Cloud migration constraint (decided 2026-07-07): the client is moving from AWS to Azure, and that migration is a contract-level blocker for anything AWS-specific. The AI tier therefore uses no AWS-only managed service: it is one Docker image plus a SQL schema, hostable on ECS today and on Azure Container Apps / AKS after migration with a config change, not a rebuild.

10. The Summarise Pipeline

One request followed end to end: what happens between the technician reaching the Review step and the 12-section ticket appearing.

1

Mobile app compiles the payload

The wizard answers (reason, parts, time, notes, completed forms, dropdowns decoded to labels) are packed client-side with zero extra API calls, then sent as POST /api/v1/summarise with the app's existing auth token.

2

.NET proxy validates & forwards

The Microservices API validates the OAuth2/Entra token, strips user credentials, adds the internal API key, and forwards server-to-server to the private FastAPI service with an extended timeout.

3

Parallel enrichment (fail-soft)

Three reads fire simultaneously against the existing APIs: dispatch details (GetAssignedDispatchesDetails), per-equipment fields (GetDispatchEquipmentFieldData), and customer procedures (GetDispatchProcedures, always fetched live, never cached). If any fetch fails, the pipeline continues without it.

4

Prompt construction

A versioned ticket standard (ticket_standard.md) forms the system instruction; the user prompt assembles dispatch context, equipment specs, completed forms, wizard answers, and procedures. Token profile ≈ 2,080 in / 1,050 out per dispatch.

5

LLM call to the client's own model

The pipeline calls qwen3-vl on the client's private gateway (measured ~6–7s per call, 30–35 tok/s; data never leaves client infrastructure). The provider abstraction in llm_client.py stays, so a different model can be swapped in by config later, but no external provider is wired up. Returns the raw ticket + procedure checks as JSON.

6

Parse, guarantee, post-process

The response is parsed and normalised against the canonical 12-section list: absent sections get an explicit MISSING placeholder, so the app always receives exactly 12 sections in standard order. Deterministic Python overrides then apply wizard-type rules (e.g. Sign-Off rebuilt from the last time entry; Refrigerant Tracking set N/A when no refrigerant was used).

7

Review, fix gaps, submit

The technician sees the ticket with per-section status badges and the procedure checklist; critical gaps must be fixed inline before submit. Submission then flows through the existing mobile-post write-back unchanged, and the accepted summary is persisted to ai.summaries.

11. API Reference

The API surface is plain REST with Pydantic models (the earlier prototype's GraphQL layer is refactored away). The service is reachable only through the .NET proxy; there is no public endpoint.

Auth model: no client talks to these routes directly. The .NET proxy is the only caller, authenticated by an internal API key plus network trust (private subnets, security groups). This keeps a single user-auth system and zero new login surfaces.

12. Retrieval, Suggestions & the Measured Baseline

Everything the copilot retrieves is deterministic SQL over the client's real dispatch history: explainable, zero new infrastructure, and already measured against a full year of staging data (252,615 dispatches). This section is what replaced the earlier vector-index plan after the 2026-07-07 architecture call.

How retrieval works

NeedMechanism
Same-site history (briefing)Keyed SQL query: past visit digests for the same customer and site, most recent first.
Similar past issues (briefing)Deterministic lookup: 2–3 recent dispatches with the same equipment type and problem code are pulled and handed to the LLM as context. No embeddings, no similarity index.
Part suggestionsSQL co-occurrence: a frequency table keyed on (equipment manufacturer type × problem code) → most-used parts, with fallback to equipment type alone, then global top parts. One SQL aggregation, fully explainable.
Compliance proceduresAlways fetched live from the source system, never cached or embedded: they are compliance-critical and change.

The measured baseline (backtested on staging, 2026-07-08)

The co-occurrence method was trained on 11 months of real dispatches and tested on the final month (4,151 dispatches with installed parts, 3,100 distinct parts in play). "Hit" means at least one actually-installed part appeared in the top-k suggestion list:

Suggestions shown (k)Hit rate
Top 118.6%
Top 331.8%
Top 539.9%
Top 1052.1%
Why this matters: with 3,100 possible parts, a zero-ML lookup already puts a right part in a 5-item list 40% of the time. This is the baseline any classical-ML model, embedding index, or LLM-heavy approach must beat to justify its added cost and complexity, exactly the "capture the baseline, commit to no accuracy numbers" framing agreed on the call.

Label-quality reality (what the EDA must account for)

An audit of the last 12 months of staging data showed the structured outcome codes are far weaker than they look: root-cause and failure codes have been dead since 2021, the problem code's top value is OTHER at 38%, and the summary code is SERVICE for 88% of filled rows. The genuine predictive signal lives in the free-text complaint (DispatchReason, 230k+ distinct values) and technician notes, plus equipment identity. Any classical-ML phase therefore must include text feature engineering; training on code columns alone will underperform the baseline above.

The vector index: optional, criteria-gated

QuestionAnswer
Is it part of this architecture?No. Decided 2026-07-07: it added infrastructure cost and operational surface without validated benefit.
When would we add it?Only if evals show deterministic retrieval misses relevant history that semantic search over the free-text fields would find, and the gain beats the baseline by enough to pay for the pipeline.
How would it slot in?Behind the existing retrieval abstraction: the briefing builder swaps its SQL lookup for a filtered similarity query; nothing else in the architecture changes. Embeddings can run on the private gateway's nomic-embed model, keeping data in client infrastructure.

13. Observability & Evals

Every AI interaction is persisted in the client's own database, so quality is measured from production reality, not vibes.

📈

The feedback loop

Log everything → corrections become ground truth → changes must beat the eval set.

  • ai.llm_calls records provider, model, tokens, latency, and outcome for every call: cost and reliability are queryable at any time.
  • ai.summary_edits records every human correction to an AI section: this is labelled ground truth generated by normal usage.
  • Eval set is built from those corrected rows and re-run before any prompt, ticket-standard, or provider/model change ships.
  • Headline metric: edit-rate per section: which of the 12 sections the AI gets right, tracked over time and per customer.
Traceability: because prompts are built from a versioned ticket_standard.md and every call is logged with its model id, any ticket in production can be traced back to exactly which standard version and model produced it.
How we view it: a lightweight dashboard page (GET /admin/dashboard) is served by the same FastAPI container and reads straight from the ai.* schema: no separate web app, no new hosting. Access is proxied through the .NET backend with an admin-role check on the existing Entra token, the same pattern as every other AI route, so the service stays fully private and no new login surface is created. Eval runs themselves are offline jobs over ai.summary_edits, not a hosted service.

14. Onboarding Plan

Everything that must be in place to take the copilot from an empty production account to live technicians. Four ordered phases: infrastructure must exist before data seeding, data before client rollout, and everything before the first AI ticket is shown to a real technician.

Phase 0 · Infrastructure provisioning (one-time)

  • Network: private subnets and an internal load balancer (idle timeout ≥ 120s); the AI service gets no public URL.
  • Container hosting ready: FastAPI image built and pushed to the registry, always-on service at min 2 instances. Cloud-agnostic by design: ECS today, Azure Container Apps / AKS after the client's migration, same image.
  • LLM connectivity: network path and API key for the client's private gateway, which serves both models (qwen3-vl for generation, nomic-embed for embeddings).
  • Secrets: the gateway key, the internal proxy API key, and the FieldJetX API token (FJX_API_TOKEN, open client item) in the secrets manager; nothing in code or images.
  • .NET proxy route deployed on the Microservices API: this is client-owned code, so it must be scheduled with their team, not ours.

Phase 1 · Data & schema seeding

  • DBA approval, then create the ai.* schema: the isolated namespace for summaries, call logs, and edits. Hard precondition for everything downstream.
  • Pin the ticket standard: ticket_standard.md version 1 agreed and frozen; every prompt and eval references a version.
  • Build the co-occurrence tables: one idempotent SQL aggregation over the last 12 months of dispatch/parts history seeds the suggestion frequency tables; refreshed as new dispatches close.
  • Procedure coverage check: verify each pilot customer's compliance procedures are current in the source system; the gap checks are only as good as the procedure list.

Phase 2 · Client rollout & app onboarding

The copilot ships inside the existing app, so rollout is an app-version story, not an account-migration story: no per-technician provisioning is needed.

+

Pilot technicians

Update to the copilot-enabled build → the Review step shows the AI ticket on their next dispatch. No sign-up, no new login: same app, same token.

↻

Everyone else

Old app versions keep today's manual review page untouched; the AI route simply is not called. Technicians join the copilot as their app updates.

  • Ship the copilot build + min-version gate for the pilot cohort before enabling the AI route for their branch.
  • Decide the assignment trigger (open client item): poll for new assignments vs a .NET hook, needed for briefings to start in the background.
  • Technician expectations: brief the pilot cohort that the AI drafts and they stay accountable: review, edit, then submit. Their edits train the eval set, so editing is contributing, not correcting a failure.

Phase 3 · Go-live sequencing

  • Monitoring/alerting live first: LLM latency and error rate, parse-failure rate, proxy timeout rate, and the edit-rate dashboard, all straight from ai.llm_calls / ai.summary_edits.
  • Pilot one customer/branch: validate briefing usefulness, ticket quality, and the gap-check loop end to end on real dispatches.
  • Baseline, then expand: capture the pilot's edit-rate and call-back baseline; roll out branch by branch once stable. Any prompt/model change after baseline must pass the eval set (Section 13).

Environments & deployment

  • Staging before prod: the copilot is validated against FieldJetX staging first (its own container service and its own ai.* schema), then promoted. No shared state across environments, so staging can never touch live customer data.
  • CI/CD: the FastAPI service ships from its own repo pipeline (build image → push to the container registry → rolling deploy; rollback = redeploy the previous image). The one .NET proxy route rides the client's existing deployment pipeline, as their strategy dictates.

16. Future Improvements

  • Voice capture: technicians dictate findings instead of typing; qwen3-vl on the private gateway is multimodal, chosen partly with this in mind.
  • Photo evidence analysis: attach and auto-describe equipment photos in the ticket; feeds the same 12-section standard.
  • Briefing push notification: proactively deliver the site briefing at assignment time (the trigger mechanism, poll vs .NET hook, is an open client item).
  • Office-side gap analytics: dashboard over ai.* data: edit-rates, recurring gap types, procedure compliance trends per customer.
  • Classical-ML suggestion model: the EDA-driven weighted model discussed on the call; ships only if it beats the measured co-occurrence baseline (hit@5 39.9%), and must include free-text features, since the label audit showed the structured codes alone carry little signal.
  • Vector index: semantic similar-incident retrieval across sites, added behind the existing retrieval abstraction only if evals show deterministic retrieval misses relevant history; embeddings can run on the private gateway's nomic-embed model.
  • Cheaper model tier: adopt a lighter model if and only if it passes the correction-based eval set.
  • Cross-customer briefing scope: whether similar-incident retrieval may look across customers is a pending client decision; retrieval filters enforce whichever answer they give.
