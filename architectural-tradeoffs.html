ClimatePros · Architectural Trade-offs

The decisions behind the revision-2 architecture · what else was on the table · what each choice costs
Decision 1

MongoDB for the AI server’s datastore

The AI server gets its own database, isolated from SQL Server. Its data is an audit trail — unstructured, unrelated, write-heavy — so a document store fits it better than a relational one.
Why
  • Isolation was requested — Paul asked for a separate DB, so a second store exists either way. Only the engine was open.
  • No relations, no joins — summaries, part results and llm_calls traces never reference each other.
  • Unstructured — LLM payloads change shape whenever prompts change. Columns would mean a migration each time.
  • Write-heavy — used for auditing: append a record per call, read back rarely. That is the document-store profile.
  • No ACID needed — nothing here is a transaction. Records are independent appends, not money or job state, so strict transactional guarantees buy us nothing.
Instead of
Ruled outReuse SQL Server — re-creates the coupling we were asked to remove.
WorkablePostgreSQL with JSONB — works, but if the payload sits in JSONB anyway we pay for a relational engine and use none of it.
Cost

One more datastore to run and back up · no engine-enforced schema, so the app validates · joining AI data to business data needs an export, not a query.

Flexible

The hard requirement is isolation, not MongoDB. If ClimatePros prefers to standardise on SQL, a separate relational instance works too — the AI server talks to its store through one repository layer, so the swap is contained.

Decision 2

Dispatch workers read SQL Server directly

The ECS Fargate workers query SQL Server directly for dispatch and technician data. They do not call back into the .NET Microservices API for it. .NET publishes the dispatch event and is then out of the loop until a technician responds — which is the point, because everything .NET runs sits on a single EC2 machine we are trying to take work off.
Why
  • It defeats the purpose — both .NET services run on one EC2 machine, shared with the legacy API. The worker exists to move dispatch load off that machine. Asking .NET for every read puts the load straight back on it.
  • Every read takes a detour — the same rows are read either way, but through .NET each read costs two network hops instead of one and holds a .NET thread while it runs. Existing endpoints are per-record, so a technician list becomes one call each.
How
Existing records — read only

The worker reads dispatch and technician data and never changes it. .NET stays the owner of that information — every write to an existing FieldJetX record still goes through .NET, so business rules and audit stay in one place.

worker reads it · only .NET writes it
New records — the worker’s own tables

Auto-Dispatch needs its own state: offers sent, cascade position, responses, claims. That goes in a few new tables the worker owns. They sit in the existing SQL Server — no new database. If the scope grows later, moving them out is a migration, not a redesign.

new tables, same database · migrate later only if needed
Instead of
Ruled outWorker asks .NET for the data — puts the shared EC2 host back in the path of every step of the cascade, which is the load the worker was built to remove.
Cost

Two codebases now read one schema, so changes to the tables the worker reads need both sides checked · the new dispatch tables share the platform database’s capacity and backups · a second connection pool on the database.

Scope

Direct access is for the dispatch path only. Inbound technician responses still arrive through .NET from the mobile app, and anything that must run existing business rules stays a .NET call.

Decision 3

Redis Streams as the dispatch message broker

The dispatch queue runs on Redis Streams. The real comparison is against Amazon SQS — the option ClimatePros put forward, and the one the team already runs. SQS clears two of the three requirements and misses the first: it is polled, and Auto-Dispatch runs on a clock.
Must meet
1 · Push-based delivery

Workers never poll. An event reaches an active worker the moment it arrives.

2 · Strict capacity cap

One Fargate worker never holds more than its configured number of dispatches at a time.

3 · FIFO queueing

Events are handed out in arrival order; anything over the cap waits in line.

Volume is not the discriminator — roughly 1,000 dispatches a day is small for all three. The discriminator is how the event reaches the worker.

Why Redis
  • It delivers, the worker does not collect — the offer moves down the ranked technician list on the schedule the algorithm sets, not on a polling rhythm.
  • It runs the timers as well as the queue — the flow is full of timed moments: act at the end of the ETA wait, move on at the end of an offer window, drop that wake-up if the technician accepts early. Those entries sit beside the queue instead of in a second system.
  • It earns its keep beyond dispatch — the same component is there for Stream 2 and whatever comes after it — caching, rate limiting, deduplication — so the ramp buys more than one queue.
Instead of
WorkableAmazon MQ — a real broker, so it meets the three requirements. Not chosen because it is a queue and nothing more: the timed wake-ups still need a second component beside it, and it bills an always-on broker to move a few hundred messages a day.
Not recommendedAmazon SQS — the team already runs it and it is the cheapest of the three, so on adoption it wins. But it is polled: the worker has to ask before it learns an event arrived.

Why polling gets in the way

Auto-Dispatch is a timing problem, not a throughput one. Every stage is a timed event — wait X seconds for ETAs, wait K seconds before the offer moves to the next technician. The queue is what makes those moments happen on time.

Pushed — the event arrives

Offer window on technician 1 expires → technician 2’s phone rings.

Polled — the event waits to be collected

Offer window expires → nothing happens until the worker next asks → technician 2’s phone rings.

  • The delay repeats at every step — the dispatch waits for a poll, then the move from technician 1 to 2 waits for a poll, then 2 to 3. Four technicians in, the job has waited four times.
  • Windows stop meaning what they say — a 30-second offer becomes 30 seconds plus the gap, so two technicians can hold the same live offer longer than intended.
  • Polling faster only shrinks it — never removes it, and the worker still has to finish waiting before it can pick up a newer, more urgent dispatch.
Cost

A component the team does not run today, so there is a learning curve and one more managed service to watch · a queue is not a system of record, so dispatch state must stay recoverable from SQL Server if it is ever lost.

Product call

If a dispatch is allowed to take longer to process, SQS is a perfectly good answer. That is a business decision, not a technical one: how quickly should a technician’s phone ring? If dispatch has to feel instant, the event must be pushed and SQS is out. If some delay is acceptable, SQS wins on familiarity — with one cost attached either way: the timed wake-ups still need a due-time table in SQL Server and something checking it.
