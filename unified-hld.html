System Diagram

What Changed Since the Walkthrough

The diagram above is revision 2. It reflects the feedback the ClimatePros team gave after the 22 Jul walkthrough; the changes below all landed on 23 Jul. The biggest one: the new dispatch tier no longer sits on a second cloud — it sits next to the platform it serves. The inventory below and its counts were rebuilt to match.

1 · The dispatch tier moved to AWS

The queue, the workers and push all now run in the same cloud as FieldJetX, beside the existing application host and the SQL Server system of record. The Auto-Dispatch path no longer crosses a cloud boundary at any point.

Container Apps · Azure Cache for Redis · Notification Hubs → ECS Fargate · message broker · Amazon SNS

2 · The AI server no longer touches SQL Server

It owns its own MongoDB for summaries, part-search results, llm_calls traces and eval data. Whatever business context a request needs travels in the request payload from the .NET AI proxy. Nothing in the AI stack holds a connection to the system of record.

AI server reads / writes SQL Server → separate store · context passed in

3 · One cross-cloud hop, and it is drawn

Only the AI stack stays on Azure — AI server, its MongoDB and the vector DB, with the models on-prem behind it. The single seam is the .NET AI proxy calling the AI server; everything else stays inside its own cloud.

every Azure tier → AWS SQL Server → one hop: .NET (AWS) → AI server (Azure)

4 · The existing platform is restated correctly

The application host running both .NET services is shown as AWS EC2, and the two additions to the Microservices API are named for what they now control: an AI proxy route and an ECS task scale monitor (workers 0→1 on the Auto-Dispatch toggle).

Azure VM · Container scale monitor → AWS EC2 · ECS task scale monitor
Decision needed

Which message broker do we standardise on?

The diagram deliberately shows an abstract message broker for the dispatch queue — the contract it has to meet is publish / consume with consumer groups and replay, and more than one managed service meets it: Redis Streams, Amazon MQ or Amazon SQS. Each carries different operational and cost trade-offs, so ClimatePros and Techjays need to agree on one before build starts — it is the one piece of the dispatch tier still unresolved.

  • MongoDB — AI-owned datastore: summaries · part results · llm_calls · evals. No SQL Server coupling.

  • Google Gemini — managed fallback only external
