New · introduced by this project

⚡ Auto-Dispatch tier + central AI server

  • Message Broker — durable job queue for Auto-Dispatch; consumer groups + replay. Implementation TBD: Redis Streams / Amazon MQ / Amazon SQS AWS
  • ECS Fargate — dispatch workers (scaling 0–1); consume the queue, read/write SQL Server AWS ECS
  • Amazon SNS — outbound push to technician phones (APNs / FCM); worker → SNS → Mobile App AWS
  • FastAPI AI Server — central AI service for all use cases; the only component that reaches the models. Two subsystems ride inside it:
    • Observability & Evals — every LLM call → llm_calls · technician edits → eval set · dashboard served here, viewed via the .NET proxy
    • Suggestion engine — lightweight LSTM / classical ML · root cause → parts + relevant dispatch
    Azure Container Apps
  • MongoDB — AI-owned datastore: summaries · part results · llm_calls · evals. No SQL Server coupling.
    Azure Cosmos DB (vCore)
  • Vector DB — embedded history index; built only if evals demand it Azure AI Search / Pinecone
  • .NET additions — AI proxy route + ECS task scale monitor on the existing Microservices API AWS EC2
  • LiteLLM Gateway + self-hosted LLM (qwen3-vl-moe / vLLM) + embedding (bge-m3) — private model infra, on-prem CP Office
  • Google Gemini — managed fallback only external
  • Observability & Tracing — abstract placeholder; OpenTelemetry distributed tracing → CloudWatch (AWS) + Azure Monitor (AI stack). Not yet designed future
