## Executive summary

**Overall score: 5.4/10 — Significant gaps — revise before build**

This is a technically substantial "how" companion to the Stream 1 Scope Document, covering deterministic Auto Dispatch (A) plus AI-assisted Job Summarisation (B) and Parts Finder (C, both technician-overridable). It is stronger than most first-draft architecture docs in its per-use-case failure-mode reasoning (§11), its self-critical, CI-gating eval loop for B, and its own candid "Open Items" appendix that already names several of this review's findings. The 5.4/10 average is independently capped by one unresolved **Blocker**: the document states models never send data to a third-party AI provider, yet includes Google Gemini as a live fallback — a contradiction the document's own Open Item #9 already flags as unresolved. Compounding this are two concrete rule mismatches against the scope document's own business rules (ranking tie-break, parts cross-tier buffer), cost figures the document itself admits are priced on the wrong cloud, and missing delivery mechanics (no CI/CD pipeline, no backup/DR for the new AI datastore, no capacity validation despite the scope document assigning that validation to this deliverable).

**Gating findings** (the ones that must close before/early in build):
- `FND-018` (Blocker) — Gemini fallback contradicts the document's "never sent to a third-party AI provider" claim; unresolved → review Gemini's data-use/DPA terms or remove the fallback, and fix the contradictory §12 language.
- `FND-002` (Major) — Ranking tie-break in §6 doesn't match scope A2 Rule 5's three-level sequence → update §6 or get sign-off to change the scope document instead.

- `FND-019` (Major) — The scope document's central PII/pricing scrubbing layer isn't described anywhere in this architecture → add it as a located component in the request flow and diagrams.
- `FND-023` (Major) — No CI/CD pipeline mechanics (tests, lint, security scanning, rollback) are described → add a CI/CD subsection.
- `FND-024` (Major) — The three largest Azure/AI-tier cost lines are self-admitted to use AWS rate cards, not real Azure pricing → re-price before using this table for any budget.

**Notable strengths:** the §11 failure-mode tables are the deepest, most concrete unhappy-path treatment of any section in the document; B's correction-based eval loop genuinely gates releases; and the document's own "Open Items" appendix already surfaces several of this review's findings, showing real self-awareness.

## Area detail

### 1. Overview & Problem Framing — 6/10
**Assessment.** The document inherits a clear problem statement from the scope document and adds a genuinely useful cover apparatus — a document-control table, a "how to read this document" section stating the cloud-placement rule up front, and an Appendix of open items. Non-goals for A/B/C (§12) closely track the scope document's out-of-scope tables. The material gap is a numeric success-criterion mismatch on Use Case B's time-savings target (see FND-001).
**Findings.** FND-001.
**Suggestions.** Align the B time-savings figure with the scope document's wording (or get sign-off on a more aggressive number and push it back into the scope document). Consider restating A and C's success measures here too, even just by reference.
**Strengths.** Document-control table, explicit reading rules, and the Open Items appendix are unusually transparent framing devices.

### 2. Architecture & System Design — 6/10
**Assessment.** Three diagrams (unified system, A detail, B&C detail) are clear and internally consistent with the prose; every component has a stated single responsibility, including explicit security-boundary design ("workers never touch SQL Server"). The gap is fidelity to the scope document's own algorithm rules — the ranking tie-break and the Parts Finder cross-tier buffer both diverge from or omit what the scope document specifies. No formal SLOs/P95 targets exist yet, honestly self-flagged as an open item.
**Findings.** FND-002, FND-003, FND-004, FND-005.
**Suggestions.** Reconcile §6's tie-break description with scope A2 Rule 5's exact three-level sequence. Add the cross-tier buffer as an explicit configuration parameter. Close the P95/SLO open item once real traffic exists.
**Strengths.** The explicit AWS/Azure/on-prem boundary rules (single SQL connection holder, single cross-cloud hop, AI server never touches SQL) are a clean, auditable security-boundary design.

### 3. Feature Flows & System Sequencing — 6/10
**Assessment.** This is the document's deepest section: full assignment-loop, two-loop, and greedy-allocation flow diagrams, paired in §11 with failure tables covering nearly every plausible failure mode. The one significant gap is a correctness edge case: the A "safe assignment" write can fail after the Redis-side dedupe has already succeeded, and this isn't addressed anywhere. A smaller gap: the scope's travel-time-over-distance preference for C sourcing isn't mentioned.
**Findings.** FND-006, FND-007.
**Suggestions.** Add the post-dedupe write-failure case to §11's A failure table. Add a line on travel-time-over-distance-with-fallback for C sourcing.
**Strengths.** The per-use-case failure-mode tables in §11 are the standout section of the whole document.

### 4. Data Schema & Modeling — 5/10
**Assessment.** Redis structures for A are modeled well — key patterns, TTLs, and purpose are explicit. The new AI-owned MongoDB collections and the vector index are described only at the collection-purpose level, with field-level schema and indexing explicitly deferred to a future client-DBA sign-off. No migration/versioning approach for the Mongo collections is discussed.
**Findings.** FND-008, FND-009.
**Suggestions.** Add a draft field list with types and a first-pass index list for each Mongo collection ahead of the DBA sign-off. State a lightweight schema-evolution approach.
**Strengths.** The Redis-structure table (Structure/Key/Purpose, TTLs, self-cleaning semantics) is a model of clarity for an ephemeral coordination layer.

### 5. API Contracts — 5/10
**Assessment.** §8 deliberately keeps the API reference brief, deferring full schemas to an unseen companion API specification. It gives a shared error envelope and explicit idempotency call-outs for safe-to-retry endpoints, but no AI model-call contract (token limits, structured-output enforcement, numeric timeout) is given anywhere, no rate limits are mentioned, and /v1 versioning only covers B.
**Findings.** FND-010, FND-011.
**Suggestions.** Add a model-call contract table (tokens, enforcement mechanism, timeout). Confirm the companion API spec exists and reference it by name; add rate limits; extend versioning to A and C.
**Strengths.** The shared error envelope and explicit idempotency call-outs are a good baseline contract for this stage.

### 6. Libraries, Frameworks & Tech Stack — 4/10
**Assessment.** Concrete libraries are named for the async/AI stack (FastAPI, Uvicorn, pydantic, httpx, redis.asyncio, aioboto3, LiteLLM), better than a spec that just says "a web framework." But nothing beyond Python 3.11+ is version-pinned, there's no licensing discussion for the self-hosted OSS models/tooling, and the embedding model's identity is internally ambiguous (the document's own Open Item #8 admits bge-m3 vs nomic-embed conflict across sections).
**Findings.** FND-012, FND-013.
**Suggestions.** Resolve and pin the embedding model name in one place. Add a version column to the stack tables and a one-line license note per self-hosted model/tool.
**Strengths.** LiteLLM as a provider-agnostic routing layer is a genuinely good lock-in mitigation for the model layer.

### 7. Observability & Traceability — 7/10
**Assessment.** The correlation-ID architecture is sound: one OpenTelemetry trace per request across every hop including the AWS→Azure span, with a shared requestId joining traces, logs, and the AI-specific Mongo collections. §12 explicitly states dispatch/customer detail is excluded from log bodies. The one real gap: llm_calls doesn't explicitly state that it captures raw prompt/completion text, the most useful artifact for debugging a bad generation.
**Findings.** FND-014.
**Suggestions.** State explicitly whether raw prompt (post-scrub) and raw output are captured per call, and for how long.
**Strengths.** Cross-cloud trace correlation and dedicated llm_calls/summary_edits collections feeding both cost and eval — a well-designed lean alternative to a third-party LLM observability tool.

### 8. Evaluation Strategy — 6/10
**Assessment.** Job Summarisation (B) has a genuinely strong, CI-gating eval loop, honestly self-critical about weak historical labels. Parts Finder (C) is comparatively thin — described only as future work for the correction-based loop, with no dataset provenance or metric restated in this document, and no re-validation trigger stated.
**Findings.** FND-015, FND-016.
**Suggestions.** Give C the same treatment as B: name the held-out set, restate the top-3 hit-rate metric here, and state what re-triggers the backtest.
**Strengths.** B's correction-based eval loop, versioned against ticket_standard.md with every call logging its model id, is a mature design for this stage.

### 9. Feedback Loops & Continuous Improvement — 7/10
**Assessment.** Both AI use cases have an explicit, well-diagrammed self-learning loop tying production corrections/usage back into future quality. Prompt/model versioning ties production behavior to a specific change. The one gap: no explicit drift-detection mechanism is named beyond the implicit edit-rate trend.
**Findings.** FND-017.
**Suggestions.** Name the edit-rate trend explicitly as the drift signal with a stated threshold, or add a dedicated drift check.
**Strengths.** Explicit, diagrammed self-learning loops for both B and C with the flywheel value spelled out in prose.

### 10. AI Compliance, Safety & Governance — 3/10
**Assessment.** Capped by an unresolved Blocker: the document claims no data ever reaches a third-party AI provider, yet Google Gemini is a live fallback in the routing diagram — a contradiction the document's own Open Item #9 already names. The scope document's central PII/pricing scrubbing-layer control also isn't described anywhere in this document, and voice-dictation capture's required cost-and-privacy assessment gate isn't addressed. Network isolation, Key-Vault secrets, and the audit trail are solid.
**Findings.** FND-018, FND-019, FND-020.
**Suggestions.** Resolve the Gemini contradiction first (review its data-use terms or remove it). Add the scrubbing layer as an explicit, located component. Add the voice-capture data flow and reference the required assessment.
**Strengths.** Network isolation, Key-Vault secret management, least-privilege read-only SQL access, and the audit-trail design are all concretely and correctly described for the primary (self-hosted) path.

### 11. Infrastructure & Environment Setup — 5/10
**Assessment.** Environments, network segmentation, and secrets management are all concretely described with per-component sizing. Two real gaps: no backup/DR policy for the new AI MongoDB store (which holds non-rebuildable original records), and no peak-concurrency/capacity model despite the scope document explicitly assigning that validation to this deliverable.
**Findings.** FND-021, FND-022.
**Suggestions.** Add an RPO/RTO statement for the Cosmos DB Mongo store. Add a capacity worksheet against the stated technician/dispatch volume.
**Strengths.** The environment-difference table and the explicit description of the single AWS→Azure network seam (interim vs. target state both stated) are clear and honest.

### 12. CI/CD & Release Management — 4/10
**Assessment.** The phased rollout model and mobile min-version gating are a genuinely good, concrete staged-exposure design, and B's eval-gate doubles as a real release gate. What's missing is everything else CI/CD normally covers: no automated build/test pipeline, and no rollback procedure for a bad Container Apps/ECS deployment.
**Findings.** FND-023.
**Suggestions.** Add a CI/CD subsection: automated test/lint gates, the eval-set gate as the documented AI-quality release gate, and an explicit rollback mechanism.
**Strengths.** The phase-gated rollout table and mobile min-version gating are a well-thought-out staged-exposure strategy.

### 13. Cost Projection — 6/10
**Assessment.** Genuine structural strength: real cost formulas, a fixed/near-fixed cost floor with named line items, and a three-scenario (Light/Typical/Heavy) table. The document is unusually transparent that its Azure/AI-tier lines are still priced on AWS rate cards. What's missing: Gemini fallback usage cost is entirely unmodeled, and on-prem GPU/hardware cost is silently excluded.
**Findings.** FND-024, FND-025, FND-026.
**Suggestions.** Get real Azure pricing before using this for budget. Add a Gemini-fallback cost line. Note the hardware exclusion explicitly and add a simple unit economic.
**Strengths.** Showing actual cost formulas and a three-scenario sensitivity table, plus proactively flagging provisional numbers, is well above the bar for this stage.

## Scope Alignment (vs. `ClimatePros-Stream1-Scope-Document.pdf`)

**Coverage — broadly strong.** Every in-scope module (A1–A4, B1–B4, C1–C3) has a corresponding technical treatment in the architecture document. Each use case's AI boundary ("system proposes, technician decides") is preserved consistently. The non-goals sections of both documents align closely (A: not route optimization, no LLM; B: never fabricates, never blocks Save; C: no price ranking, no ordering, one supplier for the POC). **No material scope creep was found** — every new infrastructure component the architecture introduces (ElastiCache, ECS Fargate, SNS, Azure Container Apps, Cosmos DB, vector store, LiteLLM, on-prem models, Gemini, the United CP Gateway) traces back to an in-scope module; the scope document explicitly defers technical architecture to this companion deliverable, so introducing this infrastructure is not creep.

Each is fixable with a targeted edit rather than a redesign — but items 2, 3, 5, and 7 in particular should be resolved with ClimatePros before this document leaves Draft status, since they affect what a team would actually build or an auditor would check against.
