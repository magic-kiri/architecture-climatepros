Environments

ClimatePros already runs Dev / Staging / Prod. Stream 1 mirrors whichever of those they ask for — Staging + Prod are the minimum; a Dev tier is provisioned only if requested. New Azure tiers (Container Apps, Redis, vector store) and the on-prem model link are stood up per environment; the AWS SQL Server system of record is shared — lower environments point at a snapshot or a restricted replica, never live prod data (see §12 PII).

Compute sizing

New Azure Container Apps tiers run small and scale horizontally — not vertically. Baseline instance is 0.5 vCPU / 1 GB RAM, which handles 60+ concurrent dispatch operations per instance comfortably; load is met by adding replicas, not bigger boxes.

Component Instance size Scaling Notes
Dispatch workers Azure 0.5 vCPU / 1 GB Scale 0–1 on Auto-Dispatch toggle 60+ concurrent dispatches per instance; one instance covers current volume
AI server (FastAPI) Azure 0.5 vCPU / 1 GB Scale 1–N on request concurrency Central B & C service; min 1 replica avoids cold-start on the model path
Azure Cache for Redis Azure Managed tier Fixed; sized to queue depth Dispatch queue must not evict — persistence on, no-eviction policy
Vector store Azure Managed / index-sized Grows with parts-history corpus Embedded dispatch-parts index (C); optional similar-incident index (B)

Network topology

All Azure compute and data tiers sit inside a single Azure VNet, subnet-segmented: Container Apps (AI server + dispatch workers) in an apps subnet, and Redis and the vector store reached over private endpoints in a data subnet — those two never expose a public IP, so all worker↔queue and AI↔vector traffic stays inside the VNet. The only public entry point is the .NET API, fronted by Azure Front Door / Application Gateway where WAF filtering and TLS termination happen; the mobile app (B, C) and web console (A) reach the API, and the API calls the AI server over internal ingress only — technician phones never hit the AI server directly.

Two private egress paths leave the VNet: the AI server reaches the on-prem model stack (LiteLLM + self-hosted models) over a VPN / private link to the ClimatePros datacenter, and falls back to Google Gemini over outbound HTTPS. The one cross-cloud path — every Azure tier to the AWS SQL Server — is the seam detailed below. That gives three trust boundaries to enforce: Internet→Azure (Front Door / WAF), Azure→AWS (VPN/peering, or public endpoint + IP allow-list as fallback), and Azure→on-prem (VPN / private link).

Cross-cloud dependency: the Azure VM (.NET API host) and both new Azure Container Apps tiers — Auto-Dispatch workers and the FastAPI AI server — all read and write the same AWS SQL Server database. Until that database itself migrates, every one of those calls crosses a cloud boundary:
  • Network path: target state is a site-to-site VPN or VNet-to-VPC private peering between the Azure subscription and the AWS VPC; until that's provisioned, the fallback is a public SQL Server endpoint locked down by IP allow-listing and TLS 1.2+.
  • Added latency: every dispatch read/write (A) and every ai.* read/write (B, C) pays inter-cloud round-trip time on top of same-region latency — this has to be budgeted into the P95 targets in §9 Observability & Evals, especially for the Auto-Dispatch worker loop's per-request SQL calls.
  • Cost: AWS bills egress on data leaving the VPC toward Azure on every query; that cross-cloud data-transfer line scales with dispatch/summary/parts-lookup volume and belongs in §10 Cost Projection alongside compute.
  • Single seam: this database is the only place Stream 1 still touches AWS — everything else in this section is Azure or on-prem. If the link goes down, all three use cases fall back to their existing manual path (phone-dispatch, forms without AI assist, no parts search) rather than failing silently.
