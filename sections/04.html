Environments

ClimatePros already runs Dev / Staging / Prod. Stream 1 mirrors all three. New AWS tiers (message broker, dispatch workers, push) and new Azure tiers (the AI server, its MongoDB, and the vector store) — plus the on-prem model link — are stood up per environment; the AWS SQL Server system of record is shared — lower environments point at a snapshot or a restricted replica, never live prod data (see §12 PII).

Compute sizing

New compute tiers — AWS ECS Fargate for dispatch workers, Azure Container Apps for the AI server — run small and scale horizontally, not vertically. Baseline instance size is 0.5 vCPU / 1 GB RAM across both, which handles 60+ concurrent dispatch operations per instance comfortably; load is met by adding replicas/tasks, not bigger boxes.

Component Instance size Scaling Notes
Dispatch workers (ECS Fargate) AWS 0.5 vCPU / 1 GB Scale 0–1 on Auto-Dispatch toggle 60+ concurrent dispatches per instance; one instance covers current volume
AI server (FastAPI) Azure 0.5 vCPU / 1 GB Scale 1–N on request concurrency Central B & C service; min 1 replica avoids cold-start on the model path
Amazon ElastiCache for Redis AWS Managed tier Fixed; sized to queue depth Dispatch queue must not evict — persistence on, no-eviction policy
Vector store Azure Managed / index-sized Grows with parts-history corpus Embedded dispatch-parts index (C); optional similar-incident index (B)

Network topology

The existing platform and all new non-AI infrastructure sit inside a single AWS VPC, matching FieldJetX: EC2 (the .NET hosts) and ECS Fargate (dispatch workers) in an apps subnet, and ElastiCache for Redis and SQL Server reached over private subnets — neither exposes a public IP, so all worker↔broker and worker↔database traffic stays inside the VPC. The only public entry point is the .NET API, fronted by an AWS load balancer / API gateway where WAF filtering and TLS termination happen; the mobile app (B, C) and web console (A) reach the API there.

A separate Azure VNet holds only the AI stack: Container Apps (the FastAPI AI server) in an apps subnet, with MongoDB and the vector store reached over private endpoints in a data subnet. The one cross-cloud path in Stream 1 is the .NET AI-proxy route on AWS calling the FastAPI AI server on Azure — technician phones never reach either side directly, and the AI server never reaches AWS SQL Server. From there, the AI server has two private egress paths of its own: the on-prem model stack (LiteLLM + self-hosted models) over a VPN / private link to the ClimatePros datacenter, and a fallback to Google Gemini over outbound HTTPS. That gives three trust boundaries to enforce: Internet→AWS (load balancer / WAF), AWS→Azure (the single AI-request hop — VPN/peering target state, public endpoint + IP allow-list as fallback), and Azure→on-prem (VPN / private link).

Cross-cloud dependency: the seam isn't the database — AWS SQL Server is read and written only by AWS-side compute (EC2 and ECS Fargate), so Auto-Dispatch (A) never leaves AWS. The one cross-cloud hop is the AI request itself: when a technician triggers a summarisation (B) or parts search (C), the .NET AI-proxy route on AWS EC2 calls the FastAPI AI Server on Azure Container Apps, carrying the job context in its payload, and gets a response back.
  • Network path: target state is a site-to-site VPN or VPC-to-VNet private peering between the AWS account and the Azure subscription; until that's provisioned, the fallback is a public HTTPS endpoint on the AI server, locked down by IP allow-listing / mTLS.
  • Added latency: only the B/C request path pays inter-cloud round-trip time — once per summarisation or parts search, not per SQL call — and this has to be budgeted into the P95 targets in §9 Observability & Evals.
  • Cost: AWS bills egress on the .NET proxy's outbound call to Azure; this is one request/response pair per B/C call, not a per-row data-transfer cost, and belongs in §10 Cost Projection.
  • Single seam: this AI-request hop is the only place Stream 1 crosses clouds — SQL Server, the message broker, the dispatch workers, and push all stay inside AWS. If the link goes down, B and C fall back to their existing manual path (forms without AI assist, no parts search); Auto-Dispatch (A) is entirely unaffected since it never touches Azure.
