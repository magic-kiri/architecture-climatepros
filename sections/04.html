Cross-cloud dependency: the Azure VM (.NET API host) and both new Azure Container Apps tiers — Auto-Dispatch workers and the FastAPI AI server — all read and write the same AWS SQL Server database. Until that database itself migrates, every one of those calls crosses a cloud boundary:
  • Network path: target state is a site-to-site VPN or VNet-to-VPC private peering between the Azure subscription and the AWS VPC; until that's provisioned, the fallback is a public SQL Server endpoint locked down by IP allow-listing and TLS 1.2+.
  • Added latency: every dispatch read/write (A) and every ai.* read/write (B, C) pays inter-cloud round-trip time on top of same-region latency — this has to be budgeted into the P95 targets in §9 Observability & Evals, especially for the Auto-Dispatch worker loop's per-request SQL calls.
  • Cost: AWS bills egress on data leaving the VPC toward Azure on every query; that cross-cloud data-transfer line scales with dispatch/summary/parts-lookup volume and belongs in §10 Cost Projection alongside compute.
  • Single seam: this database is the only place Stream 1 still touches AWS — everything else in this section is Azure or on-prem. If the link goes down, all three use cases fall back to their existing manual path (phone-dispatch, forms without AI assist, no parts search) rather than failing silently.
