2. High-Level Architecture

2a · Unified system diagram

All components Azure except the SQL Server system of record (AWS) — the single cross-cloud dependency.

The diagram groups the system into five zones — clients, the existing FieldJetX platform, the new Azure infrastructure, the private on-prem models, and a cross-cutting observability layer. What follows is the overall flow: which entity talks to which, and why. Per-use-case wiring (queues, locks, schemas, ranking, scoring) is detailed in §2b — this section stays deliberately high-level.

Entry · single front door

Web App  +  Mobile App → Azure VM (.NET APIs)

Both clients speak only to the existing .NET APIs on the Azure VM over HTTPS. Neither the new infrastructure nor the models are ever reached directly — the legacy platform stays the single entry point and gains just two new additions: an AI proxy route and a Container-scale controller (spins workers up/down).

Data · shared system of record

Azure VM  ↔  SQL Server (AWS)  ↔  Container Apps / FastAPI

The SQL Server DB is the one AWS component and the shared source of truth for all three use cases. The Azure VM reads/writes it directly; the new workers and the AI server also read/write it (job data, part stock, AI outputs). This Azure→AWS hop is the sole cross-cloud dependency.

Dispatch · Use Case A · no LLM

.NET → Redis → Container Apps → Notification Hubs → Mobile

When auto-dispatch is on, the .NET API publishes the job to Azure Cache for Redis and the scale monitor spins Container Apps workers 0→1. Workers consume the stream, rank technicians, and push accept/decline offers out through Azure Notification Hubs (APNs/FCM) to the technician's phone. The reply path returns via the .NET API. Deterministic — no model involved.

AI · Use Cases B & C

.NET → FastAPI AI Server → Vector DB  /  SQL

For summarisation (B) and parts finding (C), the .NET AI proxy forwards the request to the FastAPI AI Server — the single central AI service and the only path to the models. It queries/upserts the Vector DB for historical retrieval and reads/writes SQL to persist outputs.

Models · private, on-prem

FastAPI → LiteLLM Gateway → self-hosted LLM / embedding / Gemini

All inference goes through the on-prem LiteLLM Gateway, which routes to the self-hosted qwen3-vl-moe (vLLM) and bge-m3 embedding, with Gemini as external fallback. No service calls a model directly — LiteLLM is the sole gate, keeping data inside ClimatePros infra.

Observability · cross-cutting

all services → OpenTelemetry / Azure Monitor

Every service emits traces and logs to a shared observability layer (OpenTelemetry · Azure Monitor).

4 · Azure Cache for Redis — Infrastructure Layer New
STREAM · dispatch:stream

Tracks incoming dispatch requests per division. Durable buffer between Server A and the Container Apps workers.

MUTEX · lock:div:*

Distributed per-division lock. Guarantees sequential, non-parallel processing — no two workers touch the same division at once.

LIST · resp:{dispatchId}:{techId}

Per-technician reply channel. Azure VM API LPUSHes the Accept/Reject; the worker BLPOPs it — instant wake, no polling. EXPIRE 60s self-cleans.

⚠ Fault Tolerance — PEL Expiration & Dual-Execution Shield New

If Task C2 crashes or processing exceeds the visibility timeout, its message stays unacknowledged in the Pending Entries List (PEL):

  1. Surviving worker (e.g. C1) claims the stuck message via XCLAIM
  2. C1 must first acquire lock:div:Div_A before running the flow
  3. Guardrail: if C2 was merely slow (not dead), the live lock blocks C1 → prevents dual execution. If C2 truly died, the lock expires and C1 safely takes over.

Net effect: exactly-once dispatch to technicians — no duplicate assignments, even under crashes or stalls.
