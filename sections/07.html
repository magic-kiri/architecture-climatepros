7. Data & Schema

Three data footprints, one per use case, lifted at full fidelity from each source design. A coordinates purely through ephemeral Azure Cache for Redis structures — no data model of its own. B and C each persist AI output into their own isolated ai.* schema inside the shared AWS SQL Server, zero mixing with business tables (§3). C additionally maintains a semantic vector index over historical dispatches for retrieval.

A Auto-Dispatch — Azure Cache for Redis Data Structures

The three Redis structures that coordinate dispatch across the Container Apps worker pool. Adapted from system-design.html §6 Redis Data Structures.

StructureKeyPurpose
STREAMdispatch:streamDurable buffer of incoming dispatch requests between .NET Legacy API and the Container Apps workers. Consumed via a consumer group (XREADGROUP) — all N workers compete; each message goes to exactly one worker.
MUTEXlock:tech:{techId}Per-technician distributed lock. A request acquires locks on its candidate technicians before offering, in a fixed order (e.g. ascending techId) to avoid deadlock between overlapping requests. Requests with disjoint candidates run in parallel — even in the same division; requests sharing a technician serialize on that lock, so a tech is never double-offered. TTL self-releases on a crashed worker.
LISTresp:{dispatchId}:{techId}Per-technician reply channel. The Azure VM API LPUSHes the Accept/Reject; the worker BLPOPs it — instant wake, no polling. EXPIRE 60s self-cleans.
Concurrency: a worker processes up to 20 dispatches concurrently using async (redis.asyncio) — a blocked BLPOP on one dispatch never stalls the others.
Diagram note: the §2 architecture diagram still shows a per-division lock (lock:div:*) as a simplification. The implemented model locks per candidate technician as described here — diagram redraw pending.

C Parts Finder — Data Model

Two stores cooperate: the relational system of record (SQL Server fieldgetics) owns dispatches, inventory, and stock; the vector store — an Azure-hosted vector store — holds the semantic index used for prediction. AI-written data lands in a new ai.* schema in the same SQL Server — clear isolation from the existing tables. Adapted from usecase-C-system-design.html §6 Data Model.

New ai.* schema — AI-owned relational data

Everything the AI layer writes to SQL Server lives in its own schema: the parts lists a technician commits (with per-source allocations), prediction acceptance signals, and indexing bookkeeping. Nothing in the existing dbo tables changes — the AI footprint can be audited, backed up, or dropped independently.

Vector store — dispatch-parts index Azure

Each historical completed dispatch becomes one record, indexed for cosine similarity:

# one record per completed dispatch
id        = dispatchNo                 # stable key → idempotent upsert
document  = dispatch.reason            # the embedded text
embedding = embed(reason, DOCUMENT)    # vector (cosine / HNSW)
metadata  = { partsUsed: [ {partNo, qty}, ... ] }
Derived, not authoritative: the vector store holds only the reason text and the parts that were actually used. It is a derived, rebuildable index — the relational database remains the system of record.
