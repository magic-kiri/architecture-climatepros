12. Non-goals & PII

Two boundaries, drawn once for all three use cases instead of three times: what each use case deliberately does not do (§2 Problem & Goals in each source design draws this line explicitly, not as an omission), and what personal data this project touches. C’s source design carries the only dedicated PII inventory of the three — lifted at full fidelity below — and A’s one new piece of personal data (the device push token) was already catalogued in full where it is introduced, §11 Onboarding & Fault Tolerance.

Non-goals

Consolidated from problem-statement.html and each per-use-case design’s own “Non-goals” callout/section.

A Auto-Dispatch

  • Not route optimization — closest-available-responder, like a 911 dispatch. It ranks who answers next, not the most efficient multi-stop route.
  • Deterministic, no LLM — a weighted-sum over stated inputs with configured (not learned) weights, so every assignment is explainable and repeatable.
  • The existing manual dispatch flow is untouched — a division with the toggle OFF behaves exactly as today.
  • No UI change beyond the toggle and its configuration (task count N).
  • No change to the SQL Server system-of-record schema beyond dispatch status fields.

B Job Summarisation

  • Never fabricates. The ticket is generated from what is actually available — a missing block degrades to a MISSING placeholder, never an invented one (§6 Core Logic, §8 API Reference).
  • Never blocks Save. Every failure mode — malformed output, gateway outage, saturation — degrades to the manual recap; submission is never gated on the AI tier (§11 Fault Tolerance).
  • Completeness over prose. The headline isn’t prettier writing — that’s table stakes — it’s cross-checking the note against parts, time and photos actually logged and surfacing what’s missing.

C Parts Finder

  • No price ranking, no ordering. The tech decides where to pick a part up — the system shows the part, the place and the distance, and stops there.
  • One supplier for the POC (United, via the existing CP API Gateway); more suppliers is future work, not this scope.
  • Not replacing technician judgment — predictions are suggestions the tech can add, swap or ignore, never auto-committed.
  • No automatic purchasing or PO creation from the vendor, and no warehouse/inventory management — stock levels stay owned by the system of record.

A Device push token — see §11

Auto-Dispatch’s one new piece of personal data — the push token and its Notification Hubs deviceInstallationId (techId → deviceInstallationId) — is catalogued in full where it is introduced: encrypted at rest, access-limited to the dispatch backend, retained only while the device is active. Technician location itself is not newly stored by this project — distance/ETA reads the platform’s existing location system, unchanged and out of scope here.

B C The history B and C learn from

ClimatePros has 10–12 years of operational data — 200,000+ jobs in the last six months alone, and 16.3 million note records across the full span. It is messy by the client’s own admission: ~40% of notes are ≤40 characters, and the single most common note in the database is literally “checked history.” That is the problem B and C are solving, so it is also the data both inherit — B’s eval set (§9) and C’s retrieval index (§6, §7) are both built on it.
