Notification Hubs round-trip

The mechanics behind step 4's push — fire-and-forget out, a different path back in. Component-level diagram: §2 · Use Case A · step 3.

1

Worker publishes the offer

The winning Container Apps worker calls Azure Notification Hubs Send with the technician's device installation id and the offer payload {dispatchId, techId, job}.

2

Push is delivered

Notification Hubs fans the message out through APNs (iOS) or FCM (Android) straight to the technician's phone.

3

Technician responds

Tapping Accept/Reject in the FieldJetX app POSTs the reply to the Azure VM API, which de-dupes with SETNX resp:done and LPUSHes it onto a per-technician Redis reply list.

4

Worker wakes instantly

The same worker that sent the offer is already blocked on BLPOP for that key — no polling, no delay.

5

Rank & assign

On Accept the worker writes the assignment to SQL Server, releases the division lock, and XACKs the stream message — closing the loop.

C Parts Finder — Find & Allocate

For every requested part, the Source API returns every place it can be gathered — ordered so the technician takes the free stock first and only pays for the vendor tier when nothing else has it. This is the operational flow behind the mobile app's “source & allocate” step (§2 · Use Case C already traces the Predict/RAG path that runs before it, steps 1–6). Adapted from usecase-C-system-design.html §8 Sourcing Algorithm.

🔧 Four-Source Find → Allocate
Trigger · technician requests a part
1My truckthe technician's own van inventory · 0 mi · free
2Nearby technicians' trucksanother tech's van, modeled as a warehouse (name + warehouse code + address) · free · ranked by distance
3Branch warehouseother ClimatePros warehouses · free · nearest first
4Third-party suppliernearest United Refrigeration branch via the CP API Gateway · priced from InventorySupplierXREF.currentcost
✓Greedy allocate across the sorted listtruck first, then ascending distance; each source takes min(remaining_need, available) until the requested quantity is met
A van is a warehouse. Per operations, there is no separate “nearby technician” tier — another tech's van is modeled as a warehouse, which keeps the sourcing model to three underlying data tiers (truck / warehouse / vendor) while the technician-facing flow above still reads as four distinct sources.
Vendor lookup fails → drop the tier, not the request. If the United Refrigeration lookup fails, the vendor tier is dropped rather than failing the whole request — the technician still sees every own-stock option (truck + warehouse). See §11 Onboarding & Fault Tolerance.
