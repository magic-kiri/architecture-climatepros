9. Observability & Evals

Two different concerns share this section. Observability is operational and unified: one tracing/logging layer, introduced fresh by this project (§3 Technology Stack, §4 Infrastructure), watches all three use cases the same way. Evals are about AI output quality and only apply where a model is in the loop — Auto-Dispatch (A) is a deterministic ranking formula (§6 Core Logic) with nothing to eval; Job Summarisation (B) already has a working, production-grounded eval loop, lifted at full fidelity below; Parts Finder (C) today only validates retrieval quality on a held-out set of recent dispatches and does not yet have B’s correction-based feedback loop — closing that gap is future work, not part of this architecture.

Unified Observability — OpenTelemetry Tracing + Azure Monitor Logs

Every service in the new AI tier — the Azure VM host running both .NET APIs, both Azure Container Apps pools (Auto-Dispatch workers and the FastAPI AI server), the Redis-fed worker loop, and every vector-store call — emits OpenTelemetry traces and structured logs into a single Azure Monitor workspace (§3, §4). This was an abstract, “not yet designed” placeholder in the source design; here it is the one piece of infrastructure every use case shares, so it is specified once instead of three times.

📡 Distributed traces

One trace per request, spanning every hop it takes — .NET proxy → Container Apps → AI server → LiteLLM → model, or .NET → Redis Stream → worker → SQL Server. The cross-cloud hop to AWS SQL Server (§4) is a span like any other, so the added round-trip is visible, not hidden.

📋 Structured logs

Every service logs to Azure Monitor in one schema. Each entry carries the same requestId issued in the error envelope (§8 API Reference), so a failed call traces from the client-visible error code back through every hop it touched.

🔄 Correlation

requestId is the join key across traces, logs, and the AI-specific tables in §7 Data & Schema (ai.llm_calls, ai.summary_edits) — so a slow trace, a log line, and an eval finding for the same request all resolve to one id.

P95 targets — open item: §4 Infrastructure flags that cross-cloud AWS SQL Server round-trips must be budgeted into per-flow P95 targets, especially the Auto-Dispatch worker’s per-request SQL calls. No formal SLOs exist yet in any of the three source designs; the inputs this document already establishes are the ~1 min technician-availability window and BLPOP reply-wait timeout (A, §5 Operational Flows), the ~6–7s LLM-bound /summarise / /analyse calls (B, §8), and the <200ms / <50ms deterministic endpoints (B/C, §8). Setting numeric P95 targets per flow, inclusive of the cross-cloud SQL leg, is follow-up work once Azure Monitor is live and has real traffic to baseline against — not something any source design specified.

B Evals — the Feedback Loop

Every AI interaction is persisted in the client’s own database, so quality is measured from production reality, not vibes.

📈

The feedback loop

Log everything → corrections become ground truth → changes must beat the eval set.

  • ai.llm_calls records provider, model, tokens, latency, and outcome for every call: cost and reliability are queryable at any time.
  • ai.summary_edits records every human correction to an AI section: this is labelled ground truth generated by normal usage.
  • Eval set is built from those corrected rows and re-run before any prompt, ticket-standard, or provider/model change ships.
  • Headline metric: edit-rate per section: which of the 12 sections the AI gets right, tracked over time and per customer.
Traceability: because prompts are built from a versioned ticket_standard.md and every call is logged with its model id, any ticket in production can be traced back to exactly which standard version and model produced it.
How we view it: a lightweight dashboard page (GET /admin/dashboard, §8 API Reference) is served by the same FastAPI container and reads straight from the ai.* schema: no separate web app, no new hosting. Access is proxied through the .NET backend with an admin-role check on the existing Entra token, the same pattern as every other AI route, so the service stays fully private and no new login surface is created. Eval runs themselves are offline jobs over ai.summary_edits, not a hosted service.
The eval set inherits weak labels, not clean ones: the same audit that shaped the retrieval baseline (§6 Core Logic · B · Label-quality reality) found the structured outcome codes are mostly dead signal — root-cause/failure codes unused since 2021, problem code OTHER at 38%, summary code SERVICE for 88% of filled rows. The real predictive signal is free text (DispatchReason, technician notes). ai.summary_edits works around this because it labels the model’s actual output, not the weak structured codes — but it also means the eval set is only as good as what technicians bother to correct, not an independently audited ground truth.
