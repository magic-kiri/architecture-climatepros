3. Technology Stack

Ten layers, three use cases. The existing platform pieces — client apps, the .NET API host, SQL Server, observability — are shared: reused as-is, not rebuilt. New AI-specific infrastructure is scoped per use case: A gets a durable dispatch queue and a worker pool; B and C share a central AI service, an Azure-hosted vector store, and the same self-hosted model stack.

AWS SQL Server is the one deliberate exception, staying on AWS as Stream 1's sole cross-cloud dependency.

Dispatch Worker Stack A

Library-level detail for the Auto-Dispatch async worker (the Workers / Queue / Push rows above). Fully async top-to-bottom — no thread pools, no blocking calls in the event loop.

1Core Runtime
  • Python 3.11+
  • asyncio event loop drives all worker tasks
  • asyncio.Semaphore for concurrency control
2Push — Azure Notification Hubs
  • httpx async client against the Notification Hubs REST API
  • Direct SAS-token generation
  • Avoids thread-blocking of the legacy synchronous SDK wrappers
3Messaging & Sync — Redis
  • redis.asyncio client
  • Input: consumes job tasks via Redis Streams (XREADGROUP)
  • Wait-state: unblocked via Pub/Sub or a secondary stream when the mobile app's HTTP reply reaches the API host
4External Requests
  • httpx with built-in async connection pooling for 3rd-party API calls

Central AI Service Stack BC

Library-level detail for the shared FastAPI AI service (the Central AI service row above) — the single entry point for both B and C, and the only path to the models.

1Core Runtime
  • Python 3.11+
  • FastAPI async framework · Uvicorn ASGI server
  • pydantic request/response schemas
2Model Access
  • httpx async client to the LiteLLM gateway
  • Generation via qwen3-vl-moe (vLLM) · embeddings via bge-m3
  • Gateway handles primary + fallback routing (Gemini fallback)
3Retrieval experimental
  • Async client to the Azure-hosted vector store
  • Cosine-similarity search over bge-m3 embeddings
  • Built only if it beats the deterministic baseline — decided from the data
