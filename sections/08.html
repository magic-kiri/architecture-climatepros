8. API Reference

The full HTTP surface across all three use cases, lifted at full fidelity from each source design — every endpoint, parameter, and response shape kept intact. Only the caller-facing compute labels are updated to match this document's AWS-hosted non-AI / Azure-hosted AI infrastructure split (§2–§4) and the service renames already established there. Nothing in the request/response bodies themselves changes.

A Auto-Dispatch — API Reference

New endpoints introduced for Auto-Dispatch. Two callers: the admin dashboard (control plane — toggle & config) and the technician mobile app (data plane — push registration & replies). All existing endpoints (dispatch ingestion, dispatch status, technician location) are unchanged and out of scope here.

MethodPathCallerPurpose
POST/divisions/{id}/toggleDashboard → AWS EC2Turn auto-dispatch ON/OFF for one division. Body { enabled: bool }. On enable: pull pending requests into the stream and scale the ECS Fargate pool up; on disable: drain and scale to zero (idle = $0).
PUT/divisions/{id}/configDashboard → AWS EC2Update per-division ranking weights — distance, familiarity, priority, availability window. Body { weights: {...} }. Applied to the next assignment loop; no restart needed.
GET/divisions/{id}/configDashboard → AWS EC2Read current toggle state + weights so the admin UI can render the switch position and weight sliders. Paired read for the two writes above.
POST/devices/registerMobile → AWS EC2Register/refresh a device push token. Body { techId, platform: ios|android, token }. AWS EC2 registers the device with Amazon SNS and stores techId → platformEndpointArn. Re-posted whenever the OS rotates the token, so pushes never silently die.
POST/technicians/{id}/availabilityMobile → AWS EC2Technician reports when they will be free. Body { availableAt }. Not tied to any dispatch — it updates the technician's general availability state, which the ranking loop reads for whichever request is being processed.
POST/dispatches/{id}/respondMobile → AWS EC2Technician accepts/rejects a specific offer. Body { accept: bool }. Deduped via SETNX, then LPUSHed to resp:{dispatchId}:{techId}; the worker's BLPOP wakes instantly.

Authentication

No new auth mechanism is introduced. Every endpoint sits behind the platform's existing auth middleware, by caller:

  • Control plane (POST /divisions/{id}/toggle, PUT /divisions/{id}/config, GET /divisions/{id}/config) — behind the admin Dashboard auth, identical to the existing Dashboard endpoints. Only authenticated admins can toggle or reconfigure a division.
  • Data plane (POST /devices/register, POST /technicians/{id}/availability, POST /dispatches/{id}/respond) — behind the technician mobile-app auth, identical to the existing technician endpoints. The authenticated technician identity must match the techId/technician in the path or body.

Error contract

All endpoints return the platform's standard error envelope so a client can handle failures uniformly:

{ "code": "string",        // stable machine code, e.g. DIVISION_NOT_FOUND
  "message": "string",     // human-readable
  "requestId": "string" }  // correlation id for tracing

Global status codes apply across all endpoints:

  • 400 — malformed body / invalid field (e.g. weight out of range, unknown platform).
  • 401 — missing/invalid credentials · 403 — authenticated but not permitted (e.g. non-admin hitting a control-plane route, technician acting for another techId).
  • 404 — division / dispatch / technician not found.
  • 409 — duplicate reply on /dispatches/{id}/respond (the SETNX dedupe already rejected it); the first reply stands.
  • 500 — unexpected server error (correlate via requestId).

Two response types — two separate endpoints

The technician's two replies live at different paths because they have different scope:

  • Availability — POST /technicians/{id}/availability. Tech-scoped, no dispatchId. A general "I'm free at …" answer to the availability poll during the ~1 min ranking window; updates the technician's availability record that ranking reads.
  • Decision — POST /dispatches/{id}/respond. Dispatch-scoped. Accept/reject one specific offer; drives the offer loop, and a reject (or timeout) moves to the next ranked technician. This is the reply the worker is blocked on (BLPOP).

B Job Summarisation — API Reference

The API surface is plain REST with Pydantic models (the earlier prototype's GraphQL layer is refactored away). The service is reachable only through the .NET proxy; there is no public endpoint.

MethodRoutePurposeTypical latency
POST/api/v1/summariseWizard payload → 12-section ticket + procedure check results~6–7s (LLM-bound)
POST/api/v1/analyseTicket → gap findings + inline remediation fields; re-run until clean~6–7s
GET/api/v1/suggestionsDispatch context (equipment type + problem code) → top-k part suggestions from the co-occurrence tables; deterministic, no LLM call<200ms
GET/admin/dashboardObservability dashboard: edit-rate per section, latency, cost, parse failures, read from ai.*. Served by the same FastAPI container; no separate web app.<500ms
GET/healthLiveness probe for the Container Apps health check<50ms
Auth model: no client talks to these routes directly. The .NET proxy is the only caller, authenticated by an internal API key plus network trust (private Azure VNet, security rules). The dashboard follows the same rule: it is exposed through a .NET-proxied route with an admin-role check on the existing Entra token. This keeps a single user-auth system and zero new login surfaces.

C Technician Parts Finder — API Reference

The FastAPI AI Server exposes a deliberately small HTTP surface, reached by FJX 2.2 through the .NET Microservices API's AI proxy route — the mobile app never calls the AI layer directly, and the proxy forwards exactly the two control endpoints (/parts/predict, /parts/source).

EndpointPurpose
GET /healthLiveness / deploy probe (load-balancer + Container Apps health checks; not proxied to clients).
POST /parts/predictRAG-predicted parts for a dispatch — via the AI proxy route.
POST /parts/sourceAll sources per part — via the AI proxy route.
Scope: everything else the flow touches stays where it already lives: dispatch list/detail and the manual-add inventory tabs / catalog search are served by the existing .NET APIs, unchanged. The AI server does not serve or duplicate them — it reads the dispatch reason and stock context from the Legacy API, and calls the United CP Gateway server-side for the supplier tier.

POST /parts/predict

// request
{ "dispatchId": "..." }

// response → PredictedPart[]
[ {
  "inventoryId": "C066",
  "name":        "Condenser Fan Motor 1/4 HP",
  "partNumber":  "C066",
  "confidence":  88,          // 20–95
  "selected":    true,        // pre-selected when confidence ≥ 60
  "timesUsed":   3
} ]

Returns 503 when the prediction subsystem (embedding model / vector store) is unavailable — the client falls back to manual add. 502 on an upstream failure during prediction.

POST /parts/source

// request
{ "inventoryIds": ["C066", "24708"], "dispatchId": "...", "priority": "Normal" }

// response → SourcedPart[]
[ {
  "inventoryId": "C066",
  "name":        "Condenser Fan Motor 1/4 HP",
  "partNumber":  "C066",
  "qtyNeeded":   1,
  "sources": [ {
    "tier":        "truck",      // truck | warehouse | vendor
    "label":       "Your Truck — IL01 WH V1885",
    "detail":      "Bin C2",
    "distanceMi":  0.0,
    "qtyAvailable": 2,
    "price":       null        // null for own stock; $ for vendor
  } ]
} ]

Supplier integration — United CP Gateway (server-side, outbound)
