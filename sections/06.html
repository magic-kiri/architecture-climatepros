A Auto-Dispatch — Ranking Algorithm

This is the detail behind step 3 (“Rank the technicians”) of the assignment loop in §5. It turns each candidate's availability, distance, and visit history into a single ordered shortlist. One formula covers every case — its behavior is tuned by a single weight w chosen from the job's dispatch type.

Inputs

  • freei — minutes until technician i is available (time left on current job)
  • disti — miles from technician i to the jobsite
  • visitsi — prior visits by technician i to this customer (familiarity)
  • AVG_SPEED — average truck speed in mph, a configurable constant
  • dispatchType — Emergency · High Priority · Medium Priority
↓

Step A — unify availability + distance into one ETA

Distance can't be compared to wait-time directly. Convert distance to travel time using the average truck speed, then add the wait, so every technician collapses to one number: minutes-until-on-site. Lower is better.

travel_i = (dist_i / AVG_SPEED) * 60      # miles -> minutes
eta_i    = free_i + travel_i              # total minutes until tech is on site
↓

Step B — weighted score

Blend ETA and visit count into one score. Both must be on a 0–1 scale where higher is better, so min-max normalize each across this candidate set, then weight by w (the speed share). A pure ranking is just an endpoint: w=1 sorts by ETA only, w=0 by visits only — no separate sort needed.

speed_score_i = (eta_max - eta_i)      / (eta_max - eta_min)      # lowest eta  -> 1.0
fam_score_i   = (visits_i - visits_min)/ (visits_max - visits_min) # most visits -> 1.0

score_i = w * speed_score_i + (1 - w) * fam_score_i               # w = speed weight
# sort score_i descending -> rank 1 = offer target

Edge cases: a single candidate is rank 1 by default; if all ETAs tie the speed term is flat and familiarity breaks the tie (and vice-versa).

↓

Step C — pick w from the dispatch type

Emergency and Medium are just the two ends (w=1, w=0) of the same combined formula — so one code path serves all three.

Dispatch TypeStrategyw (speed)Result
EmergencySpeed-Based (locked)1.0Pure ETA; familiarity ignored — lowest combined time wins
High PriorityCombined0.2 (Speed 20 / Fam 80)Weighted blend; weight configurable per strategy
Medium PriorityFamiliarity-Based0.0Pure visit count — most familiar tech wins
One formula, three behaviors: the dispatch type only sets w. Emergency (w=1) reduces to pure speed, Medium (w=0) to pure familiarity, High blends them — no separate ranking code per type. The resulting ordered shortlist feeds directly into step 4 (offer to the top-ranked technician) in §5.
Future factor — skill gate: when technician skill data is available (1 ≤ skilli ≤ 5) and a job carries a minimum required skill, it enters as a hard gate, not a score term. Filter it in step 1 when building the candidate list — keep technician i only if skilli ≥ job.minSkill — so under-skilled technicians never reach ranking. The speed/familiarity scoring is untouched; only the candidate set shrinks.

B Job Summarisation — Summarise Pipeline & Retrieval

The Summarise Pipeline

One request followed end to end: what happens between the technician reaching the Review step and the 12-section ticket appearing.

1

Mobile app compiles the payload

The wizard answers (reason, parts, time, notes, completed forms, dropdowns decoded to labels) are packed client-side with zero extra API calls, then sent as POST /api/v1/summarise with the app's existing auth token.

2

.NET proxy validates & forwards

The Microservices API validates the OAuth2/Entra token, strips user credentials, adds the internal API key, and forwards server-to-server to the private FastAPI service with an extended timeout.

3

Parallel enrichment (fail-soft)

Three reads fire simultaneously against the existing APIs: dispatch details (GetAssignedDispatchesDetails), per-equipment fields (GetDispatchEquipmentFieldData), and customer procedures (GetDispatchProcedures, always fetched live, never cached). If any fetch fails, the pipeline continues without it.

4

Prompt construction

A versioned ticket standard (ticket_standard.md) forms the system instruction; the user prompt assembles dispatch context, equipment specs, completed forms, wizard answers, and procedures. Token profile ≈ 2,080 in / 1,050 out per dispatch.

5

LLM call to the client's own model

The pipeline calls qwen3-vl on the client's private gateway (measured ~6–7s per call, 30–35 tok/s; data never leaves client infrastructure). The provider abstraction in llm_client.py stays, so a different model can be swapped in by config later, but no external provider is wired up. Returns the raw ticket + procedure checks as JSON.

6

Parse, guarantee, post-process

The response is parsed and normalised against the canonical 12-section list: absent sections get an explicit MISSING placeholder, so the app always receives exactly 12 sections in standard order. Deterministic Python overrides then apply wizard-type rules (e.g. Sign-Off rebuilt from the last time entry; Refrigerant Tracking set N/A when no refrigerant was used).

7

Review, fix gaps, submit

The technician sees the ticket with per-section status badges and the procedure checklist; critical gaps must be fixed inline before submit. Submission then flows through the existing mobile-post write-back unchanged, and the accepted summary is persisted to ai.summaries.

How retrieval works

Everything the copilot retrieves is deterministic SQL over the client's real dispatch history: explainable, zero new infrastructure, and already measured against a full year of staging data (252,615 dispatches). This is what replaced the earlier vector-index plan after the 2026-07-07 architecture call.

NeedMechanism
Same-site history (briefing)Keyed SQL query: past visit digests for the same customer and site, most recent first.
Similar past issues (briefing)Deterministic lookup: 2–3 recent dispatches with the same equipment type and problem code are pulled and handed to the LLM as context. No embeddings, no similarity index.
Part suggestionsSQL co-occurrence: a frequency table keyed on (equipment manufacturer type × problem code) → most-used parts, with fallback to equipment type alone, then global top parts. One SQL aggregation, fully explainable.
Compliance proceduresAlways fetched live from the source system, never cached or embedded: they are compliance-critical and change.

The measured baseline (backtested on staging, 2026-07-08)

The co-occurrence method was trained on 11 months of real dispatches and tested on the final month (4,151 dispatches with installed parts, 3,100 distinct parts in play). “Hit” means at least one actually-installed part appeared in the top-k suggestion list:

This is the baseline any classical-ML model, embedding index, or LLM-heavy approach must beat to justify its added cost and complexity, exactly the “capture the baseline, commit to no accuracy numbers” framing agreed on the call.

Label-quality reality (what the EDA must account for)

An audit of the last 12 months of staging data showed the structured outcome codes are far weaker than they look: root-cause and failure codes have been dead since 2021, the problem code's top value is OTHER at 38%, and the summary code is SERVICE for 88% of filled rows. The genuine predictive signal lives in the free-text complaint (DispatchReason, 230k+ distinct values) and technician notes, plus equipment identity. Any classical-ML phase therefore must include text feature engineering; training on code columns alone will underperform the baseline above.

C Parts Finder — Matching & Sourcing Logic

Prediction is retrieval-augmented: find the most similar past dispatches, then rank the parts those dispatches used, weighting closeness over raw frequency so one near-identical job outranks several loosely-similar ones. Once parts are identified, the Source API works out where to get them from.

Pipeline

  1. Asymmetric embedding. Historical reasons are embedded at index time with a document task type; the live dispatch reason is embedded per request with a query task type. Both run on the self-hosted embedding model on customer hardware — dispatch text never goes to an external AI provider.
  2. Retrieve. Search the Azure-hosted vector store for the top K = 15 nearest neighbors, returning cosine distances and each neighbor's partsUsed.
  3. Rank & aggregate. The self-hosted LLM ranks & aggregates the retrieved parts: convert distance to similarity, gate on a threshold, and accumulate a cubed-similarity score per part.
  4. Confidence & select. Normalize scores, clamp to a confidence band, return the top parts, and pre-select the confident ones.

Scoring (exact)

sim            = 1 − cosine_distance
if sim > 0.55:                      # SIM_THRESHOLD — neighbor contributes
    for part in neighbor.partsUsed:
        score[part]     += sim ** 3      # closeness > frequency
        timesUsed[part] += 1

confidence(part) = clamp( round( score[part] / max_score × 95 ), 20, 95 )

return top 6 parts by score              # each pre-selected if confidence ≥ 60

The response also reports basedOn — the number of neighbors above threshold — so the client can convey how much history a prediction rests on.

Indexing & the self-learning loop

  • Idempotent upsert keyed by dispatchNo: only dispatches not already indexed are embedded, so re-runs and restarts are cheap.
  • Rate-limit-aware batching: embeddings are computed in batches with pacing and retry-with-backoff on throttling.
  • Feedback loop: when a dispatch is marked complete in SQL Server, its reason and used parts are embedded and upserted — the very next similar job benefits (the dashed learning-loop arrow in the architecture diagram in §2).

A van is a warehouse. Per operations, there is no separate “nearby technician” tier — another tech's van is modeled as a warehouse (labeled with the person's name, a warehouse code, and a street address). This keeps the model simple and reflects how stock actually moves in the field.

Ordering & allocation

  • Sort: truck first (0 mi), then all other sources by ascending distance — closest picked first.
  • Pricing: own stock (truck + warehouse) has no price; only the United vendor tier carries a dollar cost, applied from InventorySupplierXREF.currentcost.
  • Split large needs: per-source quantities are limited, so a large requested quantity is spread across sources. The client allocates greedily down the sorted list — each source takes min(remaining_need, available) until the need is met.
# greedy allocation across the sorted sources
remaining = qtyNeeded
for src in sources:            # truck first, then nearest → furthest
    take        = min(remaining, src.available)
    src.taken   = take
    remaining  -= take
    if remaining == 0: break
Vendor lookup fails → drop the tier, not the request. If the vendor lookup fails, the vendor tier is dropped rather than failing the whole request — the technician still sees all own-stock options. See §11 Onboarding & Fault Tolerance.
