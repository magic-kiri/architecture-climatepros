11. Onboarding & Fault Tolerance

Two lifecycle questions, answered separately for each use case: how does it go from an empty production environment to live technician traffic (Onboarding), and how does it behave when a dependency it relies on fails (Fault Tolerance)? A's dispatch queue, B's copilot, and C's parts predictor each have their own rollout phases and their own failure modes — only the underlying Azure services they run on (§3 Technology Stack, §4 Infrastructure) are shared. AWS service names in the two source designs are transformed to their Azure equivalents throughout; AWS SQL Server stays on AWS in every phase below, per §3/§4.

A Auto-Dispatch

Onboarding

Phase 0 — Infrastructure provisioning (one-time)

  • Azure Cache for Redis cluster up, and create the consumer group (XGROUP CREATE dispatch:stream …) — workers cannot read the stream until it exists (§7 Data & Schema · Azure Cache for Redis structures).
  • Azure Container Apps ready: worker image pushed to the registry, container app definition (1 vCPU / 2 GB), scale 0↔N policy.
  • Azure Notification Hubs registrations created — one APNs (Apple .p8 key), one FCM (Google key). Hard precondition for /devices/register: no device registration can exist until these are live.
  • Azure RBAC roles: Notification Hubs Send, Container Apps scale control, Cache for Redis access.

Phase 1 — Data seeding to DB (per division)

  • Default ranking config — seed each division's weights (distance, familiarity, priority, availability window) directly into SQL Server at production cutover.
  • Toggle default OFF — every division starts disabled. Safe default: nothing auto-dispatches until an admin explicitly opts in.
  • Escalation target — the human dispatcher/queue the "no technician accepted" path hands off to. Without it, escalation has nowhere to go.
  • Technician data readiness — each tech needs division, location source, and skills populated; ranking silently breaks on missing data.

Phase 2 — Client rollout & Notification Hubs push onboarding

Push is new to the platform, but signed-up technicians already exist on iOS/Android with no push token yet. Notification Hubs can only ring a technician once a deviceInstallationId exists — the per-device registration Notification Hubs returns when you register a push token (§8 API Reference); you send to that installation id, not the raw token. Onboarding must create it for both cohorts with no one-off migration job.

+New technician

Signs up on a push-enabled build → grants permission → POST /devices/register fires at once. Installation id exists before first dispatch. No gap.

↻Existing technician

Account exists but no token, no installation id — unreachable until they update the app, open it, and grant permission. The one cohort with a temporary gap.

  • Ship the push-enabled app + min-version gate — before enabling any division, or no one is reachable.
  • Token management — the app registers its token on first login, whenever the OS rotates it (reinstall/restore), and on a periodic (e.g. daily) refresh. Tokens stay valid for months, so this is a few calls per technician, not one per launch.
  • Backend upsert on (techId, token) — first call creates the registration, unchanged token no-ops, rotated token updates the installation id.
  • Fallback if unreachable — a tech with no installation id (or one Notification Hubs reports dead) is skipped to manual/escalation; the dispatch never hard-fails, and the tech re-registers on its next refresh.
Device token / installation id = PII. The push token and its Notification Hubs deviceInstallationId are the one new piece of personal data this project stores (techId → deviceInstallationId). They are treated as sensitive: encrypted at rest, access-limited to the dispatch backend, and kept only while the device is active — a rotated token overwrites the old id (upsert) and a dead id is cleaned up, so stale tokens do not accumulate. Technician location is not newly stored here — distance/ETA comes from the platform's existing location system, which auto-dispatch only reads, so its retention is unchanged and out of scope for this project.

Phase 3 — Go-live sequencing

  • Monitoring/alerting live first (Azure Monitor, §9) — push-adoption %, stream lag, lock-hold time, BLPOP-timeout rate.
  • Pilot one division — flip a single division ON, validate exactly-once assignment and the escalation path end-to-end.
  • Expand division-by-division — enable the rest once the pilot is clean; drop the manual fallback as installation-id adoption nears 100%.

Environments & deployment

  • Staging before prod — the change is validated in a staging environment first, then promoted to production. Staging and production each get their own isolated instances (separate Azure Cache for Redis, isolated SQL Server database, separate Container Apps service) — no shared state across environments, so a staging run can never touch live technician data.
  • CI/CD — client's existing pipeline. Auto-Dispatch is a one-time change to an existing platform, not a new service, so it introduces no new pipeline. Build, test, deploy, and rollback of the worker image and the .NET Server A/B changes all follow the client's established deployment strategy on the shared Azure VM host (§3); rollback is whatever that pipeline already provides (e.g. redeploy the previous image/revision).

Fault Tolerance

How a crashed or slow worker is handled

A dispatch request is handed to one worker to process. The system tracks that the request is "handed out but not yet finished" (§7 Data & Schema · Azure Cache for Redis structures). When the worker finishes, it marks the request done and the request clears. The goal: never lose a request if a worker dies, and never process the same request twice.

  1. Problem — worker crashes partway. The request is still marked "handed out, not finished," but nobody is actually working on it. It is stuck, and the customer waits forever.
  2. Rescue. If a request stays "not finished" for too long, another worker is allowed to take it over and process it. The stuck request is recovered.
  3. New danger. What if the first worker did not crash — just ran slow? Then the second worker takes over and processes the same request while the first is still working it — the same job offered to two technicians.
  4. Safeguard. Before offering a job, a worker must hold a claim on that technician, and only one worker can hold it at a time. If the first worker is just slow it still holds the claim, so the second worker is blocked — no double offer. If the first worker truly crashed, its claim releases automatically after a short time, so the second worker safely takes over.

The claim decides it: still held means "someone is alive and working — stay out"; released means "they are gone — go ahead."

Net effect — exactly-once: every request is processed even if a worker dies, and no request is ever processed twice even if a worker is slow. Nothing lost, nothing duplicated.

B Job Summarisation

Onboarding

Phase 0 — Infrastructure provisioning (one-time)

  • Network: private subnet and an internal load balancer (idle timeout ≥ 120s); the AI service gets no public URL.
  • Container hosting ready: FastAPI image built and pushed to the registry, always-on service at min 2 instances on Azure Container Apps — the shared central AI service (§3) that also serves C.
  • LLM connectivity: network path and API key for the client's private gateway, which serves both self-hosted models (qwen3-vl for generation, nomic-embed for embeddings) unchanged by the migration.
  • Secrets: the gateway key, the internal proxy API key, and the FieldJetX API token (FJX_API_TOKEN, open client item) in Azure Key Vault; nothing in code or images.
  • .NET proxy route deployed on the Microservices API (shared Azure VM host, §3): this is client-owned code, so it must be scheduled with their team, not ours.

Phase 1 — Data & schema seeding

  • DBA approval, then create the ai.* schema on AWS SQL Server: the isolated namespace for summaries, call logs, and edits. Hard precondition for everything downstream.
  • Pin the ticket standard: ticket_standard.md version 1 agreed and frozen; every prompt and eval references a version.
  • Build the co-occurrence tables: one idempotent SQL aggregation over the last 12 months of dispatch/parts history seeds the suggestion frequency tables; refreshed as new dispatches close.
  • Procedure coverage check: verify each pilot customer's compliance procedures are current in the source system; the gap checks are only as good as the procedure list.

Phase 2 — Client rollout & app onboarding

The copilot ships inside the existing app, so rollout is an app-version story, not an account-migration story: no per-technician provisioning is needed.

+Pilot technicians

Update to the copilot-enabled build → the Review step shows the AI ticket on their next dispatch. No sign-up, no new login: same app, same token.

↻Everyone else

Old app versions keep today's manual review page untouched; the AI route simply is not called. Technicians join the copilot as their app updates.

  • Ship the copilot build + min-version gate for the pilot cohort before enabling the AI route for their branch.
  • Decide the assignment trigger (open client item): poll for new assignments vs a .NET hook, needed for briefings to start in the background.
  • Technician expectations: brief the pilot cohort that the AI drafts and they stay accountable: review, edit, then submit. Their edits train the eval set (§9), so editing is contributing, not correcting a failure.

Phase 3 — Go-live sequencing

  • Monitoring/alerting live first: LLM latency and error rate, parse-failure rate, proxy timeout rate, and the edit-rate dashboard, all straight from ai.llm_calls / ai.summary_edits (§9 Observability & Evals).
  • Pilot one customer/branch: validate briefing usefulness, ticket quality, and the gap-check loop end to end on real dispatches.
  • Baseline, then expand: capture the pilot's edit-rate and call-back baseline; roll out branch by branch once stable. Any prompt/model change after baseline must pass the eval set (§9).

Environments & deployment

  • Staging before prod: the copilot is validated against FieldJetX staging first (its own Container Apps service and its own ai.* schema), then promoted. No shared state across environments, so staging can never touch live customer data.
  • CI/CD: the FastAPI service ships from its own repo pipeline (build image → push to the container registry → rolling deploy on Container Apps; rollback = redeploy the previous image). The one .NET proxy route rides the client's existing deployment pipeline on the shared Azure VM host, as their strategy dictates.

C Parts Finder

Onboarding

Phase 0 — Provision

  • Azure Container Apps service (private VNet) + internal load balancer; container image built in CI.
  • Azure-hosted vector store bucket + index created; connectivity to the customer-hosted embedding model and LLM configured and health-checked.
  • Network path + credentials to AWS SQL Server (reads + the new ai.* schema), the .NET Legacy API, and the United CP Gateway.
  • ai.* schema migration applied to SQL Server; AI proxy route deployed on the .NET Microservices API — the same shared route B uses (§3).

Phase 1 — Seed the index

  • Batch-embed historical completed dispatches on the self-hosted embedding model (idempotent upsert by dispatchNo).
  • Validate retrieval quality on a held-out set of recent dispatches.

This is what closes C's cold-start gap: the index is never empty at go-live, because it is seeded from the platform's own dispatch history before the first technician sees a prediction.

Phase 2 — Client rollout

  • Ship the "Add Parts with AI" / sourcing experience in the mobile app behind a feature flag, enabled per branch/division.
  • Pilot with a small technician cohort; watch acceptance rate and source mix (truck / warehouse / vendor, §6 Core Logic).

Phase 3 — Go-live & continuous learning

  • Expand the flag division-by-division.
  • Wire the on-completion re-embed pipeline so the index grows automatically as dispatches close — the self-learning loop keeps improving suggestions without a separate retraining job (§6 Core Logic).

Environments & deployment

  • Staging: isolated Azure-hosted vector index, supplier gateway on a test key — validation before each release.
  • Production: production vector index, supplier gateway on a production key — live technician traffic. No shared state across environments, matching A and B.
